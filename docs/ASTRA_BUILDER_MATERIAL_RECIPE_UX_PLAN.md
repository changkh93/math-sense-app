# 아스트라 빌더 재료·레시피·UX 확장 계획

- 작성일: 2026-08-02
- 상태: 승인 후 구현 진행 중 (단계 0~4 핵심 경로 반영)
- 대상: 아스트라 빌더 자유 건축 부지
- 상위 문서: `docs/ASTRA_BUILDER_PRODUCT_UX_TECH_DESIGN.md`
- 이 문서가 대체하는 결정: 재료 확장안의 `u16le-v2` 8·2·6비트 초안

현재 반영 범위: append-only 레시피 카탈로그(27종), `u32le-v2` 코덱과
`u16le-v1` 자동 변환, 서버 하위 호환·다운그레이드 차단, 안정 퀵바·재료함,
방향 표시, 단일 블록 재질 변경, 재질 복사 도구. 연결된 영역 변경과 동적 광원은
계획대로 보류한다.

2026-08-02 화면 QA 후 재료 계열 기반 렌더 프로필을 추가했다. 목재는 공유 절차적
결 텍스처, 유리는 형태와 무관한 투명·투과 재질을 사용한다. 퀵바 정책은 출처가
불명확한 고정 8종 대신 `기본 역할 6 + 최근 사용 2`로 확정했고, 최근 기록이 없는
두 자리에는 목재 바닥과 목재 계단을 `추천`으로 표시한다. 재료함은 형태 필터 뒤에
호환 재질만 노출하는 2단계 탐색을 사용한다.

## 1. 최종 결론

현재의 8개 블록 버튼을 계속 늘리지 않는다. 사용자는 다음 순서로 건축 조합을 만든다.

> 형태를 고른다 → 재질을 고른다 → 색상·마감을 고른다 → 완성 조합을 퀵바에서 다시 사용한다

제품과 기술의 핵심 결정은 다음과 같다.

1. 하단 팔레트는 전체 목록이 아니라 위치가 안정적인 퀵바로 바꾼다.
2. 전체 카탈로그는 건물을 가리지 않는 하단 재료함에서 연다.
3. UI와 도메인은 `형태(part)`, `재질(material)`, `변형(variant)`, `마감(finish)`으로 분리한다.
4. 저장 셀에는 완성 조합의 영구 `recipeId`를 기록한다.
5. 새 저장 포맷은 `u32le-v2`를 사용한다. 1,440셀 기준 5,760바이트로 현재 64KB 제한보다 충분히 작다.
6. 기존 `u16le-v1` 건축물은 위치와 블록 수를 유지한 채 자동 변환한다.
7. 물리·배치·보행·회전 판정은 숫자 레시피 분기가 아니라 `recipe → part → traits`로 처리한다.
8. 철거 없이 재질만 바꾸는 도구와 재질 복사를 첫 출시 핵심 기능으로 둔다.
9. 조명은 첫 출시에서 발광 재질만 사용하고 블록별 실제 광원은 만들지 않는다.
10. 재료팩 판매는 UX와 성능이 안정된 뒤 별도 단계에서 검토한다.

## 2. 현재 구현에서 확인된 제약

### 2.1 현재 UI

- `AstraBuilderHud.jsx`가 `ASTRA_BUILDER_BLOCKS` 8개를 모두 하단 버튼으로 직접 렌더링한다.
- 재료 버튼과 `방향 0°`가 같은 수준과 모양으로 섞여 있다.
- 760px 이하에서는 CSS가 5번째 버튼, 6번째 버튼, 회전 버튼을 숨긴다.
- 따라서 현재 방식으로 종류를 늘리면 모바일에서 기능이 사라지고 데스크톱에서도 탐색 비용이 급격히 증가한다.

### 2.2 현재 저장과 서버 검증

현재 셀은 `Uint16Array`이며 다음 정보를 저장한다.

```text
0~7비트   blockType
8~9비트   rotation
10비트    foundationUnderlay 존재 여부
11~15비트 미사용
```

현재 부지는 `12 × 12 × 10 = 1,440셀`이고 원시 그리드는 2,880바이트다. 서버는 `u16le-v1`만 허용하며 블록 타입 1~8을 직접 검증한다.

현재 경제상 저장 가능한 조각 수는 기본 500개, 확장 시 최대 2,500개다. 한 셀에 주 블록과 기초 바닥을 함께 둘 수 있어 물리적 최대 조각 수는 2,880개다.

### 2.3 현재 렌더링과 물리

- 동일 블록 타입은 `InstancedMesh`로 묶는다.
- 유리와 발광체는 타입 번호로 재질 속성을 분기한다.
- 외곽선은 전체 셀을 순회해 하나의 geometry로 다시 만든다.
- 물리 일부는 `astraBuilderBlockCatalog.js`의 traits를 사용한다.
- 모델·배치·렌더링에는 `blockType === 2`, `5`, `7`, `8` 같은 숫자 분기가 아직 남아 있다.

레시피 ID만 추가하고 이 숫자 분기를 그대로 두면 새 목재 계단이나 유리 바닥이 기존 계단·바닥과 같은 방식으로 작동하지 않는다. 숫자 분기 제거는 저장 포맷 변경과 같은 수준의 필수 선행 작업이다.

## 3. 검토 의견의 선별 반영

### 3.1 채택

| 의견 | 결정과 이유 |
| --- | --- |
| `u32le-v2` 사용 | 채택. 1,440셀에서 5,760바이트뿐이며 전역 레시피 ID를 주 블록과 바닥이 함께 사용할 수 있다. |
| 레시피 ID를 append-only 영구 번호로 관리 | 채택. 숫자 ID 저장 방식의 필수 조건이다. |
| 클라이언트와 Functions가 같은 카탈로그 정본 사용 | 채택. 생성 파일과 무결성 검사로 불일치를 차단한다. |
| 모든 숫자 타입 분기를 part traits로 이동 | 채택. 재질 확장과 충돌 안정성에 필요하다. |
| 편집기에 `selectedStyle` 추가 | 채택. 벽 스타일을 계단에 칠할 때 형태를 보존하기 위해 필요하다. |
| `targetSlot: main | underlay` 구분 | 채택. 같은 셀의 벽과 바닥을 정확히 선택하기 위해 필요하다. |
| 서버→클라이언트→쓰기 플래그 순서의 혼합 배포 | 채택. 오래 열린 탭의 다운그레이드 저장을 막는다. |
| 퀵바 슬롯의 세션 중 위치 안정성 | 채택. 근육 기억과 오조작 방지에 중요하다. |
| 500·1,000·2,500조각 성능 검증 | 채택. 실제 판매 중인 최대 용량까지 검증해야 한다. |
| topology와 appearance 갱신 분리 | 채택. 재질 변경으로 물리·외곽선을 다시 계산하지 않게 한다. |

### 3.2 수정하여 채택

검토안은 `u32le-v2`의 22~31비트를 모두 예약했다. 그러나 목재 바닥처럼 방향성 있는 마감을 벽 아래 underlay에도 사용할 수 있으므로 underlay 회전도 보존해야 한다. 다음처럼 2비트를 underlay 회전에 할당하고 8비트를 예약한다.

```text
0~9비트    mainRecipeId       0~1023
10~11비트  mainRotation       0~3
12~21비트  underlayRecipeId   0~1023
22~23비트  underlayRotation   0~3
24~31비트  reserved           반드시 0
```

이 배분은 다음 장점을 가진다.

- 주 블록과 기초 바닥이 같은 전역 레시피 레지스트리를 쓴다.
- 방향성 있는 목재·격자 바닥을 주 블록 아래에서도 정확히 보존한다.
- 1,023개 레시피와 8개의 예약 비트를 확보한다.
- 향후 플래그가 필요할 때 v2 안에서 제한적으로 확장할 여지가 있다.

### 3.3 첫 출시에서 보류

- 연결된 동일 재질 전체 변경
- 드래그 영역 재질 변경
- 얇은 벽, 반벽, 모서리 벽
- 난간, 대각선 지지대, 곡면
- 조명별 `PointLight`와 동적 주변광
- 퀵바 즐겨찾기와 서버 동기화
- 재료팩 판매와 가격 확정
- RGB 자유 색상 선택기
- 블록별 라이브 WebGL 미리보기

## 4. 제품 목표와 비목표

### 4.1 목표

1. 학생이 건축 화면을 떠나지 않고 재료를 찾고 미리 볼 수 있다.
2. 재료가 30종을 넘어도 하단 HUD 높이와 버튼 수가 증가하지 않는다.
3. 기존 건축물을 철거하지 않고 분위기를 바꿀 수 있다.
4. 방향이 의미 있는 형태만 회전 UI를 보여준다.
5. 기존 건축물, 로컬 초안, 충돌 복구본, 서버 저장본을 모두 보존한다.
6. 모바일에서도 조명·계단·회전을 포함한 모든 핵심 기능에 접근할 수 있다.
7. 최대 2,500조각과 여러 재료 조합에서도 지원 기기의 성능 기준을 지킨다.

### 4.2 비목표

- 무제한 재료·색상 생성
- 블록마다 광석 차감
- 첫 출시부터 수백 개의 형태
- 실제 물리 특성이 재질에 따라 달라지는 시스템
- 동시 공동 편집
- 재질 변경과 동시에 형태까지 자동 교체하는 도구

## 5. 최종 UX 구조

### 5.1 하단 퀵바

기본 구조:

```text
[재료함] [벽] [바닥] [유리] [계단] [기둥] [조명] [최근 1] [최근 2]
```

- 데스크톱은 8개 퀵슬롯, 모바일은 같은 슬롯을 가로 스크롤로 제공한다.
- 퀵슬롯 하나는 `형태+재질+변형+마감`이 완성된 레시피다.
- 숫자키 `1~8`은 데스크톱에서 슬롯과 대응한다.
- 앞의 6개는 벽·바닥·유리·계단·기둥·조명 역할을 고정 위치에 제공한다.
- 뒤의 2개는 재료함에서 고른 비기본 레시피를 최신순으로 보여준다.
- 최근 기록이 없거나 한 자리뿐이면 목재 바닥·목재 계단을 `추천`으로 채운다.
- 최근 슬롯에는 `최근`, 초기 대체 슬롯에는 `추천` 배지를 표시해 출처를 숨기지 않는다.
- 기본 6개의 위치는 사용 이력으로 바뀌지 않아 근육 기억을 보존한다.
- 최근 기록은 건축 그리드와 분리해 기기 로컬에만 저장한다.

퀵바 설정은 건축 그리드와 분리된 사용자 UI 환경설정이다. 첫 출시에서는 기기 로컬 저장으로 시작하고 서버 동기화는 사용성 확인 뒤 결정한다.

### 5.2 재료함

재료함은 데스크톱에서 화면 높이의 약 35~40%, 모바일에서 55~60%를 사용하는 하단 서랍이다. 서랍을 열어도 건물과 고스트 블록이 보인다.

정보 구조:

```text
[최근] [벽] [바닥] [계단] [기둥·보] [문·창] [조명]

형태       기본 벽 · 3칸 벽 패널 · 바닥 · 계단 · 사각 기둥 ...
재질       루멘 · 목재 · 월석 · 합금 · 유리 · 발광체
색상       서리백 · 청록 · 호두 · 현무암 · 보라 ...
마감       평면 · 홈 · 세로결 · 가로결 · 서리 ...

현재 선택  호두 목재 계단 · 가로결
```

UX 원칙:

- 형태를 먼저 고르면 호환 가능한 재질만 보여준다.
- 재질·색상 선택은 서버 저장을 일으키지 않는다.
- 선택 변경은 즉시 고스트 블록에 반영한다.
- 마감이 한 종류뿐이면 마감 행을 숨긴다.
- 잠긴 항목은 흐리게 표시하고 획득 조건만 안내한다.
- 색상만으로 구분하지 않고 결·홈·격자 아이콘을 함께 사용한다.
- 각 버튼에 별도 실시간 3D 캔버스를 만들지 않는다. 공유 렌더 또는 사전 생성 썸네일을 사용한다.

### 5.3 방향과 회전

`방향 0°`는 사용자 UI에서 제거한다.

방향이 의미 있는 형태:

- 계단
- 문
- 빛 막대
- 향후 얇은 벽, 창문, 난간, 가로 보

방향이 의미 없는 형태:

- 기본 정육면체 벽
- 기초 바닥
- 정육면체 조명
- 사각·원형 기둥

방향 컨트롤:

```text
[↶]  앞면 방향 ↑  [↷]
```

- 고스트 블록의 앞면에 화살표 또는 밝은 면 표시를 둔다.
- 좌회전과 우회전을 모두 제공한다.
- PC 단축키는 `Q/E`를 기본으로 하고 기존 `R`은 우회전 별칭으로 유지할 수 있다.
- 모바일에서도 방향 컨트롤을 숨기지 않는다.
- 형태 메타데이터의 `rotationSteps`에 따라 컨트롤을 숨기거나 제한한다.

```text
rotationSteps = 1  방향 없음
rotationSteps = 2  가로·세로 두 방향
rotationSteps = 4  네 방향
```

저장값의 rotation은 각도가 아니라 정규화된 방향 인덱스다. 클라이언트와 서버 모두 다음을 검증한다.

```text
0 <= rotation < part.rotationSteps
```

v1 데이터를 변환할 때 방향이 의미 없는 기존 블록은 0으로 정규화하고 문·계단의 방향은 보존한다.

## 6. 첫 출시 콘텐츠

### 6.1 포함

- 기존 형태 유지
- 목재 벽·바닥·계단·기둥
- 루멘 패널 4색
- 투명·청록·보라 유리 벽
- 기존 `foundation_floor` 형태를 재사용한 유리 바닥
- 별빛 조명 5색
- 신규 형태는 빛 막대 1종만 추가
- 퀵바와 재료함
- 새 방향 조작
- 단일 블록 재질 변경
- 재질 복사

### 6.2 권장 초기 재질

| 계열 | 초기 변형 |
| --- | --- |
| 루멘 패널 | 서리백, 청록, 남색, 흑연 |
| 궤도 목재 | 자작, 소나무, 호두, 탄화목 |
| 월석·세라믹 | 백색 월석, 사암, 현무암 |
| 우주 합금 | 은빛, 흑연, 구리 |
| 성운 유리 | 투명, 청록, 보라, 스모크, 서리 |
| 별빛 발광체 | 온백색, 백색, 청록, 파랑, 보라 |

기본 목재 한 종류는 무료로 제공한다. 첫 출시에서는 판매를 연결하지 않으며 해금 UI와 서버 검증 계약만 준비한다.

### 6.3 목재 표현 원칙

- 벽·기둥은 세로 나뭇결을 기본값으로 한다.
- 바닥·계단은 진행 방향을 따르는 결을 기본값으로 한다.
- 기둥 윗면은 단면 또는 나이테를 사용한다.
- 색상만 바꾼 갈색 블록이 되지 않도록 roughness와 결 패턴을 함께 적용한다.
- 첫 버전은 공유 텍스처 아틀라스 또는 절차적 텍스처를 사용하고 블록별 개별 텍스처 로드는 피한다.

## 7. 카탈로그와 영구 ID 계약

### 7.1 카탈로그 분리

정본 카탈로그는 다음 네 영역으로 나눈다.

```js
parts: {
  stair_straight: {
    renderGeometryKey: 'stair_straight',
    bodyShape: 'stair',
    heightCells: 1,
    footprint: [1, 1, 1],
    supportSurface: 'stair',
    headBlocking: true,
    doorway: false,
    underlayPolicy: 'allowed',
    rotationSteps: 4,
  }
}

materials: {
  orbital_wood: {
    acousticMaterial: 'wood',
    transparent: false,
    renderFamily: 'wood',
  }
}

recipes: {
  42: {
    id: 42,
    partId: 'stair_straight',
    materialId: 'orbital_wood',
    variantId: 'walnut',
    finishId: 'horizontal_grain',
    setId: 'orbital_wood_basic',
    deprecated: false,
  }
}
```

충돌과 보행은 part traits를 보고, 음향과 렌더 계열은 material을 본다. 레시피 ID 자체로 물리·렌더링을 분기하지 않는다.

### 7.2 영구 ID 규칙

- `0`은 빈 셀로 영구 예약한다.
- 배열 인덱스로 ID를 자동 생성하지 않는다.
- 한번 배포한 ID는 다른 레시피에 재사용하지 않는다.
- 삭제된 레시피도 제거하지 않고 `deprecated: true`로 남긴다.
- 구조적 의미가 달라지면 기존 ID를 수정하지 않고 새 ID를 발급한다.
- 배포 뒤 `recipeId`, `partId`, 점유 범위, 높이, 충돌 의미는 불변이다.
- 이름·설명·썸네일처럼 데이터 해석에 영향을 주지 않는 값만 수정할 수 있다.
- 1~8은 기존 blockType과 일치하는 legacy 레시피로 예약해 변환과 진단을 단순화한다.

### 7.3 단일 정본과 생성물

클라이언트와 Cloud Functions에서 카탈로그를 수기로 두 번 관리하지 않는다.

권장 구조:

```text
shared/astra-builder/catalog/          정본 JSON
scripts/generate-astra-catalog.mjs     생성·검증
src/.../builder/generated/             클라이언트 생성물
functions/generated/                   Functions 생성물
```

생성 단계에서 다음을 실패 조건으로 둔다.

- 중복 ID
- 배포된 ID의 의미 변경
- 존재하지 않는 part·material·variant 참조
- 허용되지 않은 형태·재질 조합
- `rotationSteps` 범위 오류
- underlay로 사용할 수 없는 part 참조
- catalogVersion 누락
- 클라이언트와 Functions 생성물 해시 불일치

## 8. `u32le-v2` 저장 계약

### 8.1 셀 레이아웃

```text
bits  0..9   mainRecipeId
bits 10..11  mainRotation
bits 12..21  underlayRecipeId
bits 22..23  underlayRotation
bits 24..31  reserved = 0
```

개념적 인코딩:

```js
word = (
  mainRecipeId
  | (mainRotation << 10)
  | (underlayRecipeId << 12)
  | (underlayRotation << 22)
) >>> 0
```

브라우저는 `Uint32Array`와 `DataView.setUint32(..., true)`를 사용한다. Functions는 `readUInt32LE`/`writeUInt32LE`를 사용한다.

### 8.2 유효성 규칙

- `mainRecipeId === 0`이면 나머지 필드는 모두 0이어야 한다.
- 단독 바닥은 main 슬롯에 바닥 레시피로 저장한다.
- 주 블록 아래 공유 바닥만 underlay 슬롯에 저장한다.
- `underlayRecipeId !== 0`이면 해당 recipe의 part가 underlay 허용 바닥이어야 한다.
- underlay가 없으면 `underlayRotation === 0`이어야 한다.
- 두 rotation 모두 해당 part의 `rotationSteps` 범위 안이어야 한다.
- reserved 비트는 반드시 0이어야 한다.
- 두 레시피 모두 카탈로그에 존재하고 deprecated 저장 허용 정책을 만족해야 한다.
- 신규 배치는 deprecated 레시피를 사용할 수 없지만 기존 저장본의 로드·재저장은 허용한다.
- 서버는 사용자의 해금 세트에 없는 신규 레시피 저장을 거부한다.

### 8.3 상태 메타데이터

```js
{
  encoding: 'u32le-v2',
  catalogVersion: 2,
  gridData,
  revision,
  blockCount,
  moduleCount,
}
```

서버 응답은 상수가 아니라 실제 저장된 `encoding`과 `catalogVersion`을 반환한다.

## 9. v1 마이그레이션

### 9.1 legacy 매핑

| v1 type | v2 legacy recipe | 기본 해석 |
| ---: | --- | --- |
| 1 | recipe 1 | 벽 조각 · 루멘 기본 |
| 2 | recipe 2 | 기초 바닥 · 청회색 |
| 3 | recipe 3 | 성운 유리 벽 · 청록 |
| 4 | recipe 4 | 발광 큐브 · 온백색 |
| 5 | recipe 5 | 직선 계단 · 루멘 기본 |
| 6 | recipe 6 | 사각 기둥 · 청회색 합금 |
| 7 | recipe 7 | 기본 문 · 호두 목재 |
| 8 | recipe 8 | 3칸 벽 패널 · 루멘 서리백 |

- v1 foundation underlay 비트는 v2 `underlayRecipeId = 2`로 변환한다.
- v1 underlay 회전은 0으로 둔다.
- 문·계단은 기존 rotation을 보존한다.
- 회전 불필요 part는 rotation 0으로 정규화한다.
- 좌표, 주/underlay 관계, 블록 수와 revision은 유지한다.
- 변환은 읽기 시 메모리에서 수행하고 v2 쓰기 플래그가 켜진 뒤 다음 저장에서 영구 기록한다.

### 9.2 로컬 초안과 복구본

IndexedDB 레코드는 `encoding`, `catalogVersion`, `ArrayBuffer`를 함께 저장한다. 로더는 v1과 v2를 모두 읽으며 알 수 없는 인코딩을 조용히 버리지 않고 복구 가능한 오류로 표시한다.

충돌 복구 키도 원본 인코딩을 보존한다. `서버본 사용`과 `기기본 적용` 모두 같은 디코더·마이그레이터를 통과해야 한다.

## 10. 안전한 혼합 버전 배포

배포 순서를 바꾸지 않는다.

1. 공통 카탈로그 생성물과 v1/v2 codec 테스트를 먼저 병합한다.
2. Functions가 v1과 v2를 모두 읽고 검증하도록 먼저 배포한다.
3. 서버가 저장된 실제 encoding과 catalogVersion을 응답하도록 배포한다.
4. 클라이언트가 IndexedDB·서버의 v1/v2를 모두 읽도록 배포한다.
5. 이 시점까지 클라이언트 저장은 계속 v1만 사용한다.
6. 관찰 기간 뒤 서버 제어 기능 플래그로 v2 쓰기를 활성화한다.
7. 서버 상태가 v2인데 클라이언트가 v1 저장을 요청하면 명시적으로 거부한다.
8. 오래 열린 탭의 오류 안내는 “새 버전으로 다시 열어 이어서 건축해 주세요”로 제공한다.
9. v2 저장·복구 안정성이 확인된 뒤 v1 쓰기 코드를 제거한다. v1 읽기는 장기간 유지한다.

다운그레이드 차단은 revision 검사와 별도로 시행한다.

```text
server encoding = v2 AND request encoding = v1
→ failed-precondition / encoding_downgrade
```

Functions 배포 없이 v2 클라이언트를 먼저 배포해서는 안 된다.

## 11. 재질 변경과 재질 복사

### 11.1 편집기 선택 상태

```js
{
  selectedRecipeId: 42,
  selectedStyle: {
    materialId: 'orbital_wood',
    variantId: 'walnut',
    finishFamily: 'wood_grain',
  }
}
```

`selectedRecipeId`는 배치와 퀵바에 사용하고 `selectedStyle`은 기존 형태에 스타일을 투영할 때 사용한다.

### 11.2 재질 변경

처리 순서:

```text
레이캐스트 대상 slot 확인
→ 대상 recipe에서 partId 확인
→ partId + selectedStyle에 맞는 호환 recipe 탐색
→ 찾으면 recipeId만 변경
→ 없으면 변경하지 않고 이유 표시
```

보존해야 하는 정보:

- 셀 위치
- main/underlay 슬롯
- partId
- 회전
- 점유 범위
- 충돌과 보행 의미

벽 스타일을 계단에 적용하면 계단 형태를 유지한 호두 목재 계단을 찾는다. 호환 레시피가 없으면 벽으로 바꾸지 않고 “이 재질은 계단에 사용할 수 없어요”라고 안내한다.

### 11.3 main과 underlay 타깃

레이캐스트와 선택 결과에 다음 값을 포함한다.

```js
targetSlot: 'main' | 'underlay'
```

- 보이는 주 블록을 클릭하면 main을 변경한다.
- 바닥 면을 명시적으로 선택하면 underlay를 변경한다.
- 고스트 강조색이나 면 하이라이트로 변경 대상을 보여준다.
- 모호한 경우 임의로 바닥을 바꾸지 않고 main을 기본으로 하되 대상 전환 UI를 제공한다.

### 11.4 재질 복사

- 스포이드로 찍은 슬롯의 recipe와 style을 선택 상태에 복사한다.
- 호환되는 완성 레시피를 퀵바의 빈 슬롯에 추가한다.
- 복사만으로 그리드 저장을 발생시키지 않는다.

## 12. 렌더링과 성능

### 12.1 렌더 그룹

- 렌더링은 `renderGeometryKey + materialRenderKey` 조합으로 인스턴싱한다.
- 불투명, 투명 유리, 발광 그룹을 분리한다.
- 첫 출시 목재는 브라우저에서 한 번 생성해 공유하는 절차적 결 텍스처를 사용하고,
  콘텐츠가 늘어나면 공유 텍스처 아틀라스로 교체한다.
- 유리 바닥은 얇은 불투명 테두리로 구멍과 구분한다.
- 첫 출시 조명은 emissive 재질만 사용하며 그림자를 생성하지 않는다.
- 실제 주변광은 첫 출시 성능 측정 뒤 가까운 6~8개 제한 방식으로 별도 검토한다.

### 12.2 topology와 appearance 분리

상태 갱신을 다음 두 계열로 분리한다.

```text
topologyRevision
  배치, 삭제, part 변경, 회전, 점유 범위 변경

appearanceRevision
  같은 part 안의 재질, 색상, 마감 변경
```

재질만 바뀐 경우 다음을 다시 계산하지 않는다.

- 충돌체
- 보행면
- 문 통로
- 점유 셀
- 외곽선 geometry

인스턴스의 재질 그룹 이동과 색상·텍스처 갱신만 수행한다.

### 12.3 성능 검증 행렬

| 조각 수 | 목적 |
| ---: | --- |
| 500 | 기본 사용자 |
| 1,000 | 확장 사용자 |
| 2,500 | 서버 최대 사용자 |

각 단계에서 활성 레시피 그룹 10·30·60개를 각각 시험한다.

측정 항목:

- 평균·하위 5% FPS
- 드로콜 수
- 불투명·유리·발광 그룹 수
- 그림자를 만드는 그룹 수
- 첫 로드와 v1→v2 변환 시간
- 한 블록 배치·삭제·회전 반영 시간
- 재질 변경 반영 시간
- 전체 외곽선 geometry 재생성 시간
- 메모리 사용량
- IndexedDB 저장과 서버 encode 시간

지원 태블릿에서 기본 500조각은 30 FPS 이상을 필수로 하고, 1,000·2,500조각은 현재 운영 빌더 대비 체감 회귀가 없어야 한다. 최대 용량에서 기준을 충족하지 못하면 재료 판매나 추가 형태 출시보다 렌더 그룹·외곽선 최적화를 먼저 한다.

## 13. 개발 단계

### 단계 0. UX 계약 시제품

- 현재 8개 legacy 레시피를 `selectedRecipeId` 인터페이스로 감싼다.
- 저장은 계속 v1을 사용한다.
- 퀵바, 재료함, 방향 컨트롤만 실제 화면에서 검증한다.
- PC·태블릿·모바일에서 HUD 겹침과 첫 재료 선택 시간을 측정한다.

완료 조건:

- 모바일에서 모든 기존 재료와 방향 기능에 접근 가능
- 재료가 30개인 모의 카탈로그에서도 하단 HUD 높이 불변
- 사용자가 설명 없이 재료함과 퀵바의 차이를 이해

### 단계 1. 카탈로그와 traits 정리

- part·material·variant·finish·recipe·set 정본 도입
- 영구 ID 레지스트리와 생성·검증 스크립트 도입
- 모델·물리·렌더링·배치의 숫자 타입 분기 제거
- `rotationSteps`, `heightCells`, `footprint`, `underlayPolicy`를 traits로 통합
- legacy recipe 1~8 등록

완료 조건:

- 물리·보행 코드에 새 recipe ID 숫자 분기 없음
- legacy 8종의 배치·삭제·회전·문 통로가 기존과 동일
- 클라이언트와 Functions 카탈로그 해시 일치

### 단계 2. v2 codec과 혼합 배포

- `Uint32Array` codec과 v1→v2 변환기 구현
- IndexedDB v1/v2 이중 읽기
- 서버 v1/v2 검증과 실제 encoding 응답
- catalogVersion 저장
- 다운그레이드 저장 거부
- 기능 플래그로 v2 쓰기 전환

완료 조건:

- 실제 v1 건축물의 좌표·조각 수·회전·underlay가 변환 전후 일치
- 서버본·기기본 충돌 해결 양쪽에서 v2 복구 성공
- 오래 열린 v1 탭이 v2 서버 상태를 덮어쓰지 못함

### 단계 3. 재료함과 첫 재료 세트

- 안정적 퀵바와 하단 재료함 정식 적용
- 루멘·목재·월석·합금·유리·발광체 초기 레시피 등록
- 고스트 실시간 미리보기
- 목재·유리·발광 렌더 그룹 구현
- 유리 바닥은 기존 floor part를 재사용
- 빛 막대 하나만 신규 part로 추가

완료 조건:

- 재료 선택만으로 로컬·서버 건축 저장이 발생하지 않음
- 투명 유리 바닥이 구멍처럼 보이지 않고 정상 보행 가능
- 방향이 필요 없는 블록에는 회전 UI가 노출되지 않음

### 단계 4. 재질 변경과 복사

- `selectedStyle`과 style resolver 구현
- main/underlay 슬롯 선택 구현
- 단일 블록 재질 변경과 undo/redo
- 재질 복사와 퀵바 추가
- 비호환 조합 안내

완료 조건:

- 재질 변경 뒤 형태·위치·회전·충돌·블록 수가 유지
- 벽 아래 바닥과 벽을 각각 정확히 변경 가능
- 재질 변경 한 번이 undo 한 번으로 복구

### 단계 5. 성능 안정화와 출시 판단

- 500·1,000·2,500조각 성능 행렬 실행
- topology/appearance 갱신 분리 확인
- 유리 정렬·드로콜·외곽선 재계산 최적화
- 사용자 테스트 후 퀵바 교체 규칙 조정
- 안정화 뒤에만 재료팩·즐겨찾기·고급 형태 다음 계획 수립

## 15. 출시 수용 기준

### 데이터 안전

- 기존 v1 건축물의 좌표와 조각 수 100% 보존
- IndexedDB 초안과 recovery 초안 모두 변환 가능
- revision 충돌과 인코딩 다운그레이드로 인한 데이터 손실 0건
- 알 수 없는 catalogVersion을 자동 덮어쓰지 않음

### UX

- 하단 HUD는 재료 수와 무관하게 고정 높이 유지
- 모바일에서 숨겨진 핵심 재료·방향 기능 0개
- 방향성 part는 현재 앞면과 다음 회전 결과를 고스트로 확인 가능
- 비방향성 part에는 불필요한 회전 조작이 없음
- 퀵바 슬롯이 단순 사용 순서 때문에 이동하지 않음

### 편집 안정성

- 재질 변경으로 형태·충돌·블록 수가 바뀌지 않음
- main과 underlay 오선택을 시각적으로 구분
- 비호환 스타일 적용은 데이터 변경 없이 설명 제공
- 배치·재질 변경 모두 기존 undo/redo 정책과 일치

### 성능

- 지원 태블릿의 500조각에서 30 FPS 이상
- 1,000·2,500조각에서 현재 운영 버전 대비 치명적 체감 회귀 없음
- 재질 변경으로 물리·외곽선 전체 재계산이 발생하지 않음
- 재료함 탐색 중 서버 저장 요청이 발생하지 않음
