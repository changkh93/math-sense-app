# 서양고전 독서 아카이브·나의 책장 구현 코드 리뷰

- 리뷰 일자: 2026-08-16
- 기준 문서: `WESTERN_CLASSIC_READING_ARCHIVE_AND_BOOKSHELF_DESIGN.md`
- 범위: 진입점, 독서 도메인/Callable Functions, 과제·관리자 연동, Firestore 규칙·인덱스·TTL, 책장/기록 UI, 감사 스크립트

## 1. 결론

기능 범위와 화면 구성은 설계 의도를 대체로 잘 구현했다. 특히 독서 로그를 별도 원장으로 두고 책 문서에는 최신/최대 페이지 투영값을 유지한 점, 서양고전 과제를 Callable 경로로 분리한 점, 클라이언트 직접 쓰기를 차단한 점은 좋은 선택이다.

다만 최초 리뷰 시점의 코드는 운영 배포 가능 상태로 판단하기 어려웠다. 관리자 검토 트랜잭션의 읽기/쓰기 순서 오류, 트랜잭션 밖 멱등 확인, 중첩 payload 해시 누락, 보상 대상 위조 가능성, 과제 수정 시 진행률 오염 등 데이터 무결성에 직접 영향을 주는 결함이 있었다. 본 리뷰 과정에서 해당 결함을 수정했다.

현재 평가는 **조건부 배포 가능**이다. 단위 테스트·정적 검사·프로덕션 빌드는 통과했지만, Firestore 에뮬레이터 통합 검증은 로컬 JDK 버전 제약으로 실행하지 못했다. JDK 21 환경에서 규칙 및 동시성 통합 테스트를 통과하고, 신규 복합 인덱스를 먼저 배포해야 최종 배포 승인으로 볼 수 있다.

## 2. 잘 구현된 부분

1. 서양고전 군집의 2D/3D 진입 정책을 공통 상수·필터로 분리했다.
2. `readingBooks`, `readingLogs`, `readingCommands`를 분리해 현재 상태, 불변 이력, 멱등 명령의 책임을 구분했다.
3. 과제 로그 ID를 `assignment__{assignmentId}`로 결정해 한 과제의 수정이 로그 중복이 아니라 revision 갱신으로 이어지게 했다.
4. 책 진행률에 `latestReadPage`와 `furthestPage`를 함께 유지해 과거 기록·재독을 표현할 수 있다.
5. Firestore 규칙에서 독서 컬렉션의 클라이언트 직접 쓰기를 차단하고 본인·관리자·연결 학부모 읽기만 허용했다.
6. 책장, 상태 필터, 페이지 기록, 독서 타임라인, 과제 도서 선택, 레거시 표시까지 사용자 흐름이 연결되어 있다.
7. 계정 삭제와 공유 스냅샷에 독서 데이터를 연결했다.

## 3. 발견 및 수정한 결함

### Critical — 수정 완료

#### 3.1 멱등 확인의 경쟁 조건

기존 코드는 `readingCommands`를 트랜잭션 밖에서 조회한 뒤 책·로그와 명령 문서를 기록했다. 같은 `commandId`가 동시에 들어오면 두 요청이 모두 “신규”로 판단해 책이나 로그를 중복 생성할 수 있었다.

수정:

- 모든 사용자 변경 Callable에서 명령 문서를 대상 데이터와 같은 트랜잭션 안에서 읽고 기록한다.
- 트랜잭션 충돌 재시도 시 이미 완료된 결과를 그대로 반환한다.
- 책 보관도 `commandId` 기반 멱등 처리에 포함했다.

#### 3.2 중첩 payload가 해시에 반영되지 않음

`JSON.stringify(payload, Object.keys(payload).sort())` 방식은 중첩 객체의 키를 누락할 수 있어 링크·첨부·독서 메타데이터가 달라도 같은 해시가 나올 수 있었다.

수정:

- 객체를 모든 깊이에서 키 정렬하는 안정 직렬화를 구현했다.
- 중첩 키 순서는 같게, 중첩 값 변경은 다르게 해시되는 회귀 테스트를 추가했다.

#### 3.3 관리자 검토 트랜잭션 실행 실패

기존 검토 함수는 과제 문서를 쓴 뒤 독서 로그를 읽었다. Firestore 트랜잭션은 모든 읽기가 쓰기보다 먼저 와야 하므로 실제 호출이 실패할 수 있었다.

수정:

- 과제, 사용자, 독서 로그를 모두 읽은 뒤 과제·로그·사용자·광석 원장을 기록하도록 순서를 재구성했다.

#### 3.4 관리자 보상 대상 및 원장 무결성

기존 서버는 클라이언트가 보낸 `userId`를 보상 대상으로 사용할 수 있었고, 잔액만 바꾸며 `crystal_transactions` 원장을 남기지 않았다. 보너스 상한도 없었다.

수정:

- 보상 대상은 항상 과제 문서의 `userId`만 사용한다.
- 보상은 0~10,000 정수로 제한한다.
- `bonusLedgerVersion`과 결정적 원장 ID를 사용해 과제, 잔액, 원장을 한 트랜잭션에서 갱신한다.
- 검토 관리자 UID를 기록한다.

#### 3.5 과제 수정 시 책 진행률 오염

기존 코드는 과제 revision이 페이지를 낮추거나 읽은 시각을 바꿔도 증분 계산만 했다. 수정 전 로그가 최대 페이지였으면 `furthestPage`가 잘못 남고, 최신 로그 투영도 어긋날 수 있었다.

수정:

- 신규 제출은 O(1) 증분 계산을 사용한다.
- 기존 과제 로그 수정은 해당 책의 유효 로그에서 기존 revision을 교체한 뒤 최신/최대 진행률을 재계산한다.
- 동일 시각의 최신 로그 판정은 문서 ID 내림차순 규칙과 일치시켰다.

### High — 수정 완료

#### 3.6 레거시 과제 수정 시 중복 과제 생성

클라이언트가 기존 `docId`를 서버에 전달하지 않아 임의 ID 레거시 과제를 수정하면 새 결정적 ID 과제가 추가될 수 있었다.

수정:

- 기존 과제 ID를 Callable에 전달한다.
- 서버는 기존 문서의 소유자·날짜·서양고전 군집을 검증하고 같은 문서를 갱신한다.

#### 3.7 관리자 도서 정정의 교차 사용자 연결 및 부분 반영

기존 함수는 새 책이 과제 소유자의 책인지 확인하지 않았고, 과제/로그 변경 뒤 책 진행률을 트랜잭션 밖에서 재계산했다. 중간 실패 시 불일치가 남을 수 있었다.

수정:

- 과제 소유자의 활성 도서만 연결할 수 있다.
- 과제·로그·기존 책·새 책 진행률을 같은 트랜잭션에서 갱신한다.
- 정정 관리자와 시각을 기록한다.

#### 3.8 날짜·시각 검증과 최근 7일 경계

정규식만 통과하면 `24:99`, `2026-02-30` 같은 값이 허용될 수 있었고, 최근 7일 조건이 오늘+이전 7일로 총 8일을 허용했다.

수정:

- 실제 달력 날짜와 00:00~23:59를 엄격히 검증한다.
- 미래 시각 입력을 차단한다.
- 제출 범위를 오늘 포함 7일(차이 0~6일)로 통일했다.
- 클라이언트 시간 유틸과 기간 프리셋도 같은 경계로 수정했다.

#### 3.9 검토 전 과제와 연결된 책 보관

책을 보관한 뒤 보완 요청을 받으면 잠긴 책 때문에 과제를 수정하지 못할 수 있었다.

수정:

- 잠기지 않은 과제 로그가 연결된 책은 검토 완료 전 보관할 수 없도록 차단했다.

### Medium — 수정 완료

#### 3.10 기간 필터 페이지 누락

기존 독서 기록은 20개를 먼저 가져온 뒤 클라이언트에서 기간을 필터링했다. 최근 7일 기록이 20개 바깥에 있으면 첫 화면이 비거나 일부 결과가 누락될 수 있었다.

수정:

- `readDateKst` 범위를 Firestore 쿼리에 포함했다.
- 기간+책/출처/이벤트 조합의 복합 인덱스 4개를 추가했다.
- 커서에 `readDateKst`, `readAt`, 문서 ID를 함께 사용한다.

#### 3.11 책 상세 화면의 오래된 상태

상태 변경 뒤 drawer가 처음 전달받은 책 객체를 계속 보여 주어 완독/중단 배지가 즉시 바뀌지 않았다.

수정:

- 상세 화면에서 책 단건 쿼리를 다시 읽어 최신 상태를 렌더링한다.

#### 3.12 읽는 중인 책의 상태 변경 경로 부재

읽는 중인 책 카드는 클릭 시 페이지 입력만 열어 상세 drawer에 들어갈 수 없었다. 따라서 읽는 중 → 완독/중단 변경 UI가 사실상 막혀 있었다.

수정:

- 카드에 별도 `상세·상태` 버튼을 추가했다.

#### 3.13 진입점 필터의 부분 문자열 중복 허용

제목 `includes` fallback 때문에 “네버랜드 클래식 복사본” 같은 추가 지역도 노출될 수 있었다.

수정:

- canonical ID 우선, 정확한 제목 fallback으로 각 대상당 한 개만 선택하고 정해진 3개 순서로 반환한다.
- 여기에 아스트라 프론티어, 과제 기록소, 다크 매터, 나의 책장을 합쳐 7개 진입점을 유지한다.

#### 3.14 감사 스크립트가 Git에서 제외됨

구현 완료 보고서에 포함된 감사 스크립트가 `.gitignore` 패턴에 걸려 커밋 산출물에 포함되지 않았다.

수정:

- 해당 파일만 추적하는 예외 규칙을 추가했다.
- 전체 assignments 스캔을 서양고전 cluster `in` 쿼리로 축소했다.
- 인증 후보 경로와 실패 종료 코드를 보완했다.

제약:

- Firestore 에뮬레이터 규칙 컴파일은 Firebase CLI가 JDK 21 이상을 요구하지만 현재 환경이 JDK 17이라 실행되지 않았다.
- 운영 Firestore 대상 감사 스크립트는 읽기 비용과 운영 데이터 접근을 수반하므로 이번 리뷰에서는 실행하지 않았다.
- 기존 대형 화면 파일 전체 ESLint에는 이번 기능과 무관한 선행 오류가 남아 있다. 신규 독서 모듈 대상 ESLint는 통과했다.

## 5. 배포 전 필수 체크리스트

1. JDK 21 환경에서 Firestore 규칙 컴파일 및 권한 테스트를 실행한다.
2. 학생 직접 쓰기 거부, 본인/관리자/연결 학부모 읽기, 타인 읽기 거부를 에뮬레이터로 검증한다.
3. 동일 `commandId` 동시 2회 호출 시 책/로그가 한 건만 생기는 통합 테스트를 실행한다.
4. `firestore.indexes.json`을 먼저 배포하고 모든 신규 인덱스가 `READY`인지 확인한다.
5. Functions와 Hosting을 배포한다.
6. 테스트 계정으로 책 등록 → 페이지 기록 → 과제 제출 → 보완 요청 → 재제출 → 승인 → 광석 원장 확인을 수행한다.
7. 읽는 중 책의 보관 차단, 검토 완료 뒤 보관 성공, 레거시 과제 수정 시 문서 ID 유지 여부를 확인한다.
8. 운영 감사 스크립트를 읽기 전용 자격 증명으로 실행하고 레거시/비정상 스키마 수를 보관한다.

## 6. 잔여 개선 권고

1. 과제 revision과 관리자 도서 정정은 정확성을 위해 책의 로그를 재조회한다. 한 책의 로그가 수천 건으로 늘어나는 규모가 예상되면 별도 repair job 또는 집계 구조를 검토한다.
2. Callable 동시성, 규칙, 원장 보상은 현재 순수 함수 단위 테스트만으로 충분하지 않다. Firestore Emulator Suite 기반 통합 테스트를 CI에 추가한다.
3. 감사 스크립트에 `--project`, `--json`, 사용자 표본 제한 옵션을 추가하면 운영 점검 자동화가 쉬워진다.
4. 전체 저장소 ESLint 선행 오류는 별도 정리 작업으로 분리해 신규 기능의 lint gate를 CI에 적용한다.
