# 아스트라 프론티어 확장 계획

작성일: 2026-09-06. 상태: 현황 조사 및 실행 설계 완료, 게임 기능 변경·배포 전.

## 1. 방향과 조사 범위

**내가 만든 섬을 걷고, 날고, 바닷속까지 탐험하며 발견한 것으로 다시 꾸미는 힐링 창작 게임**을 목표로 한다. 기본 이동과 창작은 부담 없이 제공하고, 성장은 새로운 표현 도구·서식지·이야기를 여는 방식으로 설계한다.

사용자 요청은 현황 파악과 대규모 개선 계획이다. 첨부 화면은 관찰 자료로만 사용했다. 저장소 코드, 기존 문서와 관련 테스트를 확인했으며 운영 배포본과의 일치 여부, 실사용 기기 FPS, 이용자 통계, 실제 청구액은 확인하지 않았다. 아래 비용·일정·성능 목표는 확정 견적이나 실측 운영 수치가 아니다.

비용 효율은 개발 유지보수, 서버 운영, 이용자의 재화·시간 부담을 모두 포함한다. 엔진 교체보다 기존 Three.js/React Three Fiber, 건축 데이터, Firebase 구조의 재사용을 우선한다.

## 2. 확인된 현황

| 영역 | 코드에서 확인한 현재 상태 | 개선 판단 |
| --- | --- | --- |
| 월드 | 로우폴리 시설·자연물, 지형·강·바다 렌더링, 방문·복구·로버·수집 콘텐츠 | 기존 세계관과 모델 재사용 가치가 높음 |

| 실시간 방문 | Firebase Realtime Database 위치·방향·크기, 변화량 기준 전송, 5초 heartbeat | 위치를 Firestore에 옮길 이유가 없음. 전송량과 방 구독 범위 계측 우선 |

| 이동 범위 | 클라이언트 presence 정규화 x/z ±32, y -8~24 | 높은 비행·깊은 잠수 전 렌더·정규화·DB 규칙·경계 동시 점검 |
| 코드 구조 | GalaxyWorld3D.jsx 5,970줄, functions/galaxyGame.js 5,250줄 | 해당 기능을 건드릴 때 이동·카메라·장비·생태계를 점진 분리 |

주요 근거 파일:

- `src/components/GalaxySocial/GalaxyWorld3D.jsx`: Astronaut, FrontierScene, 캐릭터·카메라·상호작용.
- `src/components/GalaxySocial/GalaxyTerrainModel.js`, `GalaxyTerrain3D.jsx`: 지형 높이와 물 표현.
- `src/components/GalaxySocial/builder/`: 건축 모델, 충돌, 렌더, 저장 및 동기화.
- `src/hooks/useGalaxyWorldPresence.js`, `database.rules.json`: 실시간 위치와 접근 규칙.
- `src/components/GalaxySocial/MetaGalaxy.jsx`, `functions/galaxyGame.js`: 영속 데이터와 서버 게임 처리.

기존 `docs/astra-builder-multilevel-design.md`는 역사적 설계 자료다. “빌더에서 항상 이동 정지”, “360블록 제한”, “원격 크기 미동기화”, “u16만 사용” 등의 설명은 현재 코드와 다르다. 이를 신규 작업량으로 계산하지 않는다.

첨부 화면에서는 시설과 기둥이 캐릭터 주변을 크게 가리고, 작은 캐릭터 대비 시설 밀도가 높으며, 상단 정보가 여러 곳으로 나뉜다. 이는 화면 한 장의 관찰이며 카메라 버그나 성능 저하를 입증하지는 않는다. 실제 플레이 QA에서 가림·길 찾기·상호작용 선택을 확인한다.

## 3. 이용자 경험 설계

### 3.1 자유와 힐링을 유지하는 기본 루프

산책 → 발견·관찰 → 재료/색상/설계도 획득 → 집·정원·수족관 꾸미기 → 친구 초대·사진 → 다음 탐험으로 이어진다. 퀘스트는 추천 활동으로 접을 수 있게 하고 휴식·장식만 해도 만족할 수 있게 한다.

기본 블록·수영·조감 시점은 빠르게 제공한다. 기본 비행 장비와 잠수 장비는 짧은 체험으로 해금하고, 이후 성장은 외형·조작 특성·탐험 콘텐츠로 확장한다. 현재 학습 보상과 탐험 시간 정책은 유지한 상태에서 시작하며 시간 종료 시 비행·잠수 중에도 안전 귀환되도록 한다. 학습 보상은 희귀 꾸미기 선택지를 넓히되 기본 창작의 반복 비용을 높이지 않는다.

### 3.2 장비 비행과 bird view

- 장비 슬롯: 등(날개/호버팩), 몸(잠수복), 발(오리발), 손(도구). 외형과 능력 데이터를 분리한다.
- 첫 비행은 **호버팩**: 이륙·정지 비행·상승·하강·안전 착륙. 공중에서 멈출 수 있어 건축과 조작 학습에 유리하다.
- 다음 장비는 글라이더: 활공·상승기류·완만한 선회. 호버팩과 같은 이동 시스템에 프로필만 추가한다.
- 시점은 1인칭/3인칭/조감/사진 모드로 분리한다. 조감은 높은 위치에서 섬을 내려다보며 회전·줌·캐릭터 추적·북쪽 고정·즉시 복귀가 가능해야 한다.
- 조감 모드는 비행 능력과 독립적으로 제공한다. 카메라만 멀어져도 캐릭터가 순간 이동하거나 원격 채집되지 않는다. 공중 건축의 설치 거리는 캐릭터 기준으로 검증한다.
- 천장·나무·건물·월드 경계 충돌을 처리한다. 장비 해제·탭 복귀·시간 종료 시 낙하 방치 대신 안전 위치로 복귀한다.
- 힐링 기본 모드는 반복 연료 결제 없이 비행 가능하도록 제안한다. 장거리 원정에만 선택적 배터리/휴식 규칙을 두고 복귀를 막지 않는다.

### 3.3 수영과 해양 탐험

- 장비 없이 수면 수영 가능. 물 진입/나오기, 뜨기, 이동, 해안 오르기부터 완성한다.
- 잠수복 장착 시 잠수·상승·정지 부유, 오리발로 이동 특성 변경. 모바일에 상승/하강 버튼을 추가한다.
- 첫 바다는 얕은 만 한 구역: 모래 바닥·해초·산호·어류 6~8종·관찰 도감·사진·수족관 장식으로 시작한다. 물고기 개체 수는 기기별 예산 안에서 정한다.
- 물고기는 탐지 반경·무리 이동·피하기·서식지 선호 같은 단순 규칙을 공유한다. 일상 유영은 클라이언트에서 계산하고 도감 등록·보상만 서버 검증한다.
- 수중 안개·색감·기포·음향·수면 양면 표현을 넣어 물 아래라는 느낌을 만든다. 고가의 실시간 굴절·유체 시뮬레이션은 초기 범위에서 제외한다.
- 기본 관찰 모드에서는 산소 압박을 없애거나 매우 완만하게 둔다. 깊은 원정의 산소 소진은 보유 아이템 손실 없이 구조·복귀로 처리한다.
- 심해 유적·동굴·해저 집은 후속 확장이다. 먼저 밀폐 공간·공기 주머니·출입 경계가 검증되어야 한다.

### 3.4 창작 도구와 이용자 비용

- 이동하며 짓기와 설계 시점을 유지하고, 영역 선택·복제·대칭·색 변경·미리보기·실행 취소를 확장한다.
- 집·다리·정원 설계도는 저장하고 재배치할 수 있게 한다. 공유 설계도는 모델/셀 데이터만 포함하고 임의 스크립트를 실행하지 않는다.
- 기본 연습 공간은 재료 소비 없이 실험한다. 실제 섬 반영 전 필요한 재료를 표시하고 한 번에 확정한다.
- 자신이 지은 물체 철거는 사용 재료를 되돌리되, 선물·보상 재료 복제나 환급 반복이 일어나지 않도록 출처와 작업 ID를 서버에서 관리한다.
- 블록 개수만 줄이는 방식 대신 반복 부재 묶음 렌더, 멀리 있는 물체 단순화, 부지 분할로 창작 규모를 키운다.
- 친구 방문은 감상/설계도 공유부터 확장하고, 공동 편집은 별도 권한·충돌 처리가 마련된 후 제공한다.

## 4. 기술 실행 설계

### 4.1 이동과 카메라

제안 모듈: `movement/frontierLocomotion.js`, `movement/frontierWaterVolumes.js`, `camera/FrontierCameraRig.jsx`, `equipment/frontierEquipmentCatalog.js`. 명칭은 구현 시 저장소 관례에 맞춰 확정한다.

이동 상태는 grounded / airborne / flying / swimming / diving / recovering으로 나눈다. 카메라 상태는 별도로 둔다. 입력 → 장비 능력 확인 → 물/지면 판정 → 속도 적분 → 충돌 해결 → 상태 전환 → 애니메이션·카메라 순으로 처리한다.

현 이동 루프의 `groundHeight + jump.height` 최종 대입에 비행 높이를 끼워 넣으면 다음 프레임에 지면으로 끌려갈 수 있다. 절대 발 높이와 수직 속도를 공통 상태로 두고 지상 점프부터 동일한 해결기로 연결한다. 기존 계단·문·캐릭터 크기 충돌 테스트를 유지한다.

물은 시각 메시와 별도로 수면 높이·바닥 높이·경계·깊이를 반환하는 volume 질의를 제공한다. 입수와 출수의 작은 여유 구간을 달리해 수면에서 상태가 반복 전환되지 않게 한다. 공중 채집과 수중 상호작용은 기존 XZ 거리만으로 판정하지 않고 3차원 거리·도달 가능성·활동 모드를 확인한다.

큰 프레임 지연은 제한된 시간 간격과 이동 소단계로 처리한다. 카메라 충돌·가림 완화는 캐릭터 충돌과 독립적으로 처리한다. 조감은 가시거리와 그림자 범위를 함께 제한하고 멀리 있는 부지는 축약 표현한다.

### 4.2 데이터·동기화·보상

- 영속: 장비 소유/장착, 해금, 도감, 보상 기록은 Firestore와 서버 함수. 장비 구매·장착·보상 지급은 소유권·허용 ID·중복 작업을 검사한다.
- 일시 상태: 위치·방향·이동 모드·장비 외형은 기존 RTDB. 카메라 각도와 물고기 매 프레임 위치는 저장하지 않는다.
- RTDB 필드 및 좌표 범위를 바꾸면 `database.rules.json`과 정규화·원격 렌더를 함께 갱신하고 규칙 테스트를 추가한다. 클라이언트 clamp만으로 유효성을 보장하지 않는다.
- 클라이언트 이동은 반응성을 위해 로컬 처리하되, 위치 보고만으로 희귀 보상을 주지 않는다. 서버가 탐험 시작·허용 구역·시간·중복 등록을 검증한다.
- 첫 생태계는 방문자마다 유영 위치가 약간 달라도 허용한다. 같은 물고기를 함께 포획하는 경험은 공유 개체와 보상 경합 설계가 필요한 별도 단계다.
- 구형 저장을 읽고, 신형 필드는 기본값을 제공한다. 마이그레이션 전 복구 가능성과 충돌 초안 보존을 검증한다.

## 5. 비용 효율과 측정 방법

| 비용 영역 | 우선 조치 | 확인 지표 |
| --- | --- | --- |
| 개발 | 기존 엔진·저장·메시 재사용, 기능 접점만 모듈 분리 | 기능별 투입 인일, 회귀 수정 시간 |
| GPU/배터리 | 반복 물체 InstancedMesh, 거리별 LOD, 그림자·투명 효과 품질 단계 | 기기별 p95 프레임 시간, draw calls, 메모리 |
| 실시간 통신 | 변화 없으면 전송 생략 유지, 방 구독 계측, 필요 시 구역 구독 | 플레이어 시간당 다운로드 바이트, 방 인원별 증폭 |
| 영속 저장 | 기존 3초/10초 저장 유지, 도감·보상만 서버 처리 | 플레이어 시간당 읽기·쓰기·함수 호출 |
| 에셋 | 공통 지오메트리/재질, 압축 및 캐시, 신규 지역 지연 로딩 | 첫 진입/재방문 다운로드량 |
| 콘텐츠 | 어종별 모델보다 공통 몸체+색+크기+행동 프로필 | 신규 콘텐츠 제작 시간 |

RTDB는 전송량 중심이고 Firestore는 읽기·쓰기 등 작업량을 계산한다. 이를 동일한 “DB 호출당 비용”으로 합산하지 않는다. Firestore 리스너 갱신도 읽기 비용에 영향을 준다. [RTDB 과금](https://firebase.google.com/docs/database/usage/billing), [Firestore 과금](https://firebase.google.com/docs/firestore/pricing).

예시 계산(추정용): DAU 1,000명 × 하루 20분 × 30일 = 월 10,000 플레이어 시간. 이동 활성 비율 50%, 4.5회/초, 패킷 150바이트, 평균 수신 상대 3명이라면 위치 데이터 다운로드는 약 `10,000×3,600×0.5×4.5×150×3` = 36.45GB/월이다. 프로토콜·암호화·heartbeat·초기 동기화·재접속은 별도이며 실제 과금량은 더 클 수 있다. 이것은 현재 서비스의 측정값이 아니다.

월 총비용은 RTDB 다운로드·저장 + Firestore 읽기·쓰기·저장 + 함수 실행 + 에셋 전송·저장으로 산정한다. 실제 지역·요금제·청구 내역을 확보한 뒤 단가를 적용한다. 개발비는 아래 인일 × 실제 인일 단가로 계산하며 외주 에셋 비용을 따로 둔다.

비행은 시야 확장 때문에, 수중은 투명 렌더와 생물 업데이트 때문에 비용이 늘 수 있다. 같은 장면·기기·체류 시간으로 전후 비교하고, 개선 목표는 기존 기능의 시간당 운영 비용 유지, 확장 체험은 초기 기준 대비 +20% 이내로 제안한다. 목표를 넘으면 생물 시뮬레이션 거리·구독 범위·그림자부터 줄인다. 아직 달성한 수치가 아니다.

InstancedMesh는 반복 geometry/material의 draw call을 줄이는 데 사용하고, LOD는 카메라 거리에 따른 표현 선택에 사용한다. 이미 적용된 곳은 유지하고 실제 프로파일에서 병목인 물체에 확대 적용한다. [Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html), [LOD](https://threejs.org/docs/pages/LOD.html).

## 6. 우선순위·일정·완료 조건

개발자 1명과 필요 시 아트/QA 지원을 전제로 한 초기 계획 범위다. 1인일은 집중 작업일이며 병렬 인력 투입에 선형 비례하지 않는다. 0단계 측정 후 다시 산정한다.

| 단계 | 예상 인일 | 결과물 | 통과 조건 |
| --- | --- | --- | --- |
| 0. 기준선·구조 정리 | 3~5 | 재현 장면, 성능·통신 계측, 이동/카메라 경계 분리 | 기존 건축·방문·저장 테스트 및 실제 조작 회귀 통과 |
| 1. 비행·조감 MVP | 5~8 | 호버팩 1종, 장착 UI, 상승/하강/착륙, 조감/복귀 | 건물 충돌·장비 해제·모바일·시간 종료·재접속 안전 |
| 2. 수영·잠수 MVP | 6~10 | 수면 수영, 잠수복·오리발, 얕은 만, 물 표현 | 물 경계·교량·물속 카메라·출수·안전 귀환 통과 |
| 3. 창작·생태 콘텐츠 | 8~12 | 어종 6~8종, 관찰 도감·수족관, 설계도·복제 | 발견→장식 루프, 보상 중복 방지, 저장 복구 |
| 4. 확장 검증·출시 | 5~8 | 기기별 품질, 방문 동기화, 단계 배포·롤백 | 성능·비용·저장 기준 충족 및 운영 모니터링 |

총 27~43인일, 주 5일 집중 개발 기준 약 6~9주. 통합 위험 대응 20~30%를 더하면 약 33~56인일이다. 정식 아트 제작·대규모 공동 편집·심해 동굴·무한 지형·플레이어 거래는 별도 산정한다.

실행 백로그는 다음 순서로 진행한다.

1. AF-001: 동일 행성의 지상/건축/조감 기준 장면과 장치별 계측 확보.
2. AF-002: 기존 동작을 보존하면서 이동 상태와 카메라 정책 분리.
3. AF-003: 장비 카탈로그·서버 소유권·장착/해제·기본값 구현.
4. AF-004: 비행/조감과 안전 귀환, AF-002/003 의존.
5. AF-005: 물 volume·수영/잠수, AF-002 의존.
6. AF-006: 수중 표현·생물·도감 검증, AF-003/005 의존.
7. AF-007: 설계도·복제·재료 미리보기·환급의 멱등 처리.
8. AF-008: 비용·모바일·다중 방문 검증과 단계 출시.

첫 검토 가능한 산출물은 “기존 섬에서 호버팩 장착 → 이륙 → 조감 → 착륙 → 기존 건축 계속하기”가 끊김 없이 되는 수직 기능 묶음이다. 비행과 수영을 한 번에 대규모 교체하지 않고 이 단위로 통합 위험을 줄인다.

## 7. 검증과 출시 기준

- 현재 조사에서 통과: `npm run test:astra-builder`, `npm run test:galaxy-terrain`, `npm run test:galaxy-navigation`, 서버 builder/live 테스트, `npm run test:astra-builder:performance`.
- CPU 벤치마크: 500/1,000/2,500부재에서 topology 약 1.01~1.11ms, instances 2.06~2.20ms, collision 2.25~2.59ms, codec 약 0.02ms. 인코딩 문자열 7,680바이트. 로컬 Node 측정이며 브라우저 전체 FPS나 서버 처리 성능으로 해석하지 않는다.
- 목표 기기: 데스크톱·중급 Android·iPhone/iPad에서 실제 모델/OS를 기록한다. 제안 목표는 데스크톱 p95 프레임 20ms 이내, 모바일 33ms 이내이며 기기 선정 후 확정한다.
- 필수 이동 사례: 계단·문·천장·작은 캐릭터/큰 캐릭터, 공중 장비 해제, 물 위 비행, 입수/출수 반복, 수중 점프 입력, 탭 숨김 복귀, 통신 끊김, 탐험 시간 종료.
- 필수 데이터 사례: 구형 저장 불러오기, 저장 중 종료, 재접속 복구, 충돌 초안, 중복 구매/보상/환급, 허용되지 않은 장비 ID, 좌표 범위, 구형 클라이언트 접속.
- 사용성 기준: 신규 사용자 5명 이상이 안내 후 이륙·조감 복귀·잠수·출수·꾸미기를 도움 없이 수행하는지 관찰한다. 만족도·멀미·막힘 구간도 기록한다.
- feature flag로 장비 비행·잠수·생태계를 각각 제어한다. 내부 QA → 제한 사용자 → 전체 순으로 노출하며 단계별 48시간 이상 저장 오류·프레임·전송량을 관찰한다.
- 저장 유실·보상 중복·반복적인 월드 이탈은 즉시 노출 중단 조건이다. 롤백 시 새 장비/도감 데이터는 보존하고 기능만 숨긴다. 비행/잠수 중인 캐릭터는 안전한 지상 위치로 복귀시킨다.

현재 남은 운영 확인 항목은 배포본 리비전, 목표 지원 기기, DAU/동시 방문 인원, 평균 체류 시간, Firebase 비용 내역, 아트/QA 인력이다. 이 정보가 없어도 0단계와 로컬 시제품 준비는 진행할 수 있으나 월 운영비와 출시일을 확정할 수는 없다.
