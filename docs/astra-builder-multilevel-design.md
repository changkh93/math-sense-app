# 아스트라 빌더 캐릭터 이동형 다층 건축 설계안

## 1. 결론

아스트라 빌더의 핵심 문제는 계단 높이 함수 하나가 아니라, 현재 빌더가 **캐릭터가 멈춘 평면 편집기**로 설계되어 있다는 점이다. 빌더 진입 시 캐릭터 이동이 정지되고, 조이스틱이 사라지며, 부지 중심 Orbit 카메라와 수동 층 편집면이 설치 위치를 결정한다.

목표 구조는 다음과 같다.

> 캐릭터가 기존 월드 이동 카메라로 건물 안팎을 걸어 다니면서, 화면 중심으로 바라본 블록 면에 설치·삭제하고, 계단의 보행 표면을 따라 위층으로 이동한다. 수동 층 선택과 부지 전체 카메라는 보조 설계도 모드로 남긴다.

가장 효율적인 개발 방법은 새 물리 엔진을 도입하거나 저장 포맷을 교체하는 것이 아니다. 현재 Three.js/R3F와 `Uint16Array` 복셀 그리드를 유지하면서 아래 세 계층만 분리한다.

1. 블록별 정적 물리·건축 규칙
2. 캐릭터의 3D 이동 해결기
3. 카메라 Raycast 기반 설치 대상 해결기

## 2. 현재 코드에서 확인된 실제 원인

### 2.1 빌더 모드가 캐릭터를 명시적으로 정지시킨다

- `GalaxyWorld3D.jsx`에서 빌더 활성 중 `Astronaut`에 `paused={paused || builderActive}`를 전달한다.
- 같은 상태에서 1인칭을 강제로 끄고, 이동 조이스틱도 렌더링하지 않는다.
- `AstraBuilderPlot.jsx`는 빌더 활성 시 부지 중심을 바라보는 별도의 `OrbitControls`를 기본 카메라로 등록한다.

따라서 “이동하며 짓기”를 먼저 가능하게 하지 않으면 계단과 3D 충돌을 구현해도 사용자가 체감할 수 없다.

### 2.2 보행 높이는 y=0 한 셀만 본다

`getAstraBuilderWalkSurfaceOffset`은 월드 좌표를 항상 y=0 셀로 바꾸고, 기초 바닥이면 낮은 오프셋을, 아니면 플랫폼 높이를 반환한다. 현재 플레이어의 발 높이, 위층 바닥, 계단 회전, 머리 공간을 입력받지 않는다.

### 2.3 빌더 충돌은 2D 원형 반경이며 y=0~1만 장애물이다

`isAstraBuilderWalkBlockingCell`은 y가 2 이상이면 모두 통과시키고, `builderBlockColliders`는 각 블록을 수평 원형 장애물로 바꾼다. 이동 루프도 XZ 거리만 비교한다. 이 구조에서는 다음을 구분할 수 없다.

- 같은 XZ에 있는 1층 벽과 2층 플레이어
- 발 아래 바닥과 몸 앞의 벽
- 계단 경사면과 계단의 높은 옆면
- 머리 위 천장과 통과 가능한 빈 공간

### 2.4 설치는 3D 면 조준이 아니라 수동 층 편집면이 중심이다

- `activeLayer` 높이에 투명 편집 plane을 놓고 해당 plane의 XZ 위치로 셀을 고른다.
- 기존 블록 설치는 윗면만 허용하며 측면은 거부한다.
- 계단의 윗면을 누르면 다음 계단 좌표를 제안하는 로직은 이미 있으나, 일반 측면 설치·거리 제한·플레이어 겹침 검사와 통합되어 있지 않다.
- 블록을 누를 때 `activeLayer`를 대상 셀의 층으로 바꾸므로, 플레이어 층·조준 층·수동 층이 한 상태에 섞여 있다.

### 2.5 문은 데이터와 렌더링 양쪽에서 예외 처리된다

문 한 셀을 배치하면 회전 방향의 이웃 열까지 출입구로 간주하고, 낮은 층의 다른 블록을 렌더링과 충돌 목록에서 제외한다. 시각적으로는 2셀 너비 문이지만 저장 데이터에는 1셀만 들어간다. 현재 단계에서 문 열림 상태까지 추가하면 범위가 크게 늘어나므로, 1차 목표에서는 “항상 열린 2셀 출입구”로 명시하는 편이 안전하다.

## 3. 목표 사용자 경험

### 기본 플레이-빌드 모드

- 빌더를 열어도 WASD/방향키와 모바일 조이스틱으로 계속 이동한다.
- 기본 카메라는 기존 캐릭터 추적 카메라를 재사용한다.
- 실내와 정밀 건축에서는 1인칭 전환을 허용한다.
- 화면 중앙 조준점이 가리키는 블록 면을 기준으로 반투명 설치 미리보기를 표시한다.
- 설치, 삭제, 회전은 조준 대상에 적용한다.
- 플레이어가 서 있는 셀이나 몸·머리와 겹치는 위치에는 설치할 수 없다.

### 계단과 다층 이동

- 계단 낮은 쪽에서 접근하면 회전 방향을 따라 연속적으로 올라간다.
- 높은 쪽 옆면과 잘못된 방향의 진입은 벽처럼 막힌다.
- 계단 위 머리 공간이 부족하면 올라가지 못한다.
- 계단 끝에 유효한 바닥이 있으면 끊김 없이 해당 층으로 전환한다.
- 위층 바닥 가장자리에는 명시된 낙하 정책을 적용한다.

### 보조 설계도 모드

- 기존 부지 전체 Orbit 카메라와 층 엘리베이터는 삭제하지 않고 “설계도/개요 모드”로 이동한다.
- 이 모드에서는 `manualLayer` 편집면을 사용할 수 있다.
- 플레이-빌드 모드의 실제 설치 좌표는 `manualLayer`가 아니라 Raycast 결과가 결정한다.

## 4. 설계 원칙

### 4.1 저장 데이터와 런타임 규칙을 분리한다

현재 셀 값은 블록 타입과 회전만 저장한다. 이 포맷은 그대로 유지한다. 물리와 설치 규칙은 블록 카탈로그의 정적 메타데이터로 둔다. 따라서 기존 로컬 초안, 서버 `u16le-v1`, 리비전 충돌 처리, 360블록 제한을 마이그레이션 없이 재사용할 수 있다.

권장 블록 속성은 다음과 같다.

| 속성 | 목적 |
| --- | --- |
| `bodyShape` | 몸통과 충돌하는 단순 형상 |
| `supportSurface` | 발을 지지하는 평면·경사·없음 |
| `walkable` | 보행 표면 후보 여부 |
| `headBlocking` | 머리 공간 검사 포함 여부 |
| `raycastShape` | 조준에 사용하는 형상 |
| `buildFaces` | 블록을 붙일 수 있는 면 |
| `placementRule` | 문·계단 등 특수 배치 규칙 |
| `acousticMaterial` | 기존 충돌·발소리 재사용 |

1차 블록 정책은 아래처럼 명시한다.

| 블록 | 몸 충돌 | 발 지지 | 특수 규칙 |
| --- | --- | --- | --- |
| 루멘 벽 | 전체 셀 | 윗면 | 일반 턱으로는 오를 수 없음 |
| 기초 바닥 | 얇은 박스 | 실제 렌더 상단 | 현재 높이값 유지 |
| 성운 유리 | 전체 셀 | 윗면 | 투명해도 충돌 |
| 별빛 조명 | 제품 결정 필요 | 기본 없음 | 장식물로 시작 권장 |
| 기본 계단 | 경사+높은 옆면 | 방향성 경사 | 회전 4방향 |
| 지지 기둥 | 가는 박스 | 기본 없음 | 렌더 폭과 충돌 폭 일치 |
| 나무 문 | 문틀만 | 없음 | 1차는 항상 열린 2셀 출입구 |

### 4.2 플레이어는 점이나 AABB가 아니라 수직 원기둥으로 본다

현재 캐릭터는 +/− 입력으로 기본 `0.28`에서 최소 `0.14`, 최대 `0.70`까지 `0.04` 단위로 변한다. 따라서 고정된 충돌체를 사용하지 않고, 현재 스케일 비율로 수평 반경·몸 높이·눈 높이·머리 여유 공간을 함께 계산한다. 현재 코드는 수평 충돌 반경 일부만 스케일에 맞춰 보정하므로, 이를 수직 충돌과 빌더 배치 검사까지 확장한다.

스케일 비율은 `현재 캐릭터 스케일 / 기본 캐릭터 스케일`로 정의한다. 기본 수평 충돌 반경 `0.14`와 계측된 기본 몸 높이에 이 비율을 적용한다. 블록은 AABB 또는 계단 전용 단순 형상, 플레이어는 수평 원형 단면을 가진 수직 원기둥으로 처리한다.

충돌 조건은 “같은 y층”이 아니라 다음 두 조건의 동시 충족이다.

1. 플레이어 원과 블록의 XZ 영역이 겹친다.
2. 플레이어의 발–머리 구간과 블록의 아래–위 구간이 겹친다.

X와 Z 이동을 분리해 기존 벽 미끄러짐 조작감을 보존한다. 프레임 드롭 때 벽을 통과하지 않도록 이동 거리가 셀 크기의 일정 비율보다 크면 2~4개 소구간으로 나누어 검사한다. 현재 부지는 12×12×10, 최대 360블록이므로 외부 물리 라이브러리나 복잡한 옥트리는 불필요하다.

### 4.2.1 캐릭터 크기 변경과 건축물의 조화

캐릭터 크기에 따라 물리 공간이 실제로 달라지는 정책을 사용한다.

- 작아지면 낮은 천장, 좁은 통로, 계단 아래 공간을 통과할 수 있다.
- 커지면 반경과 키가 함께 증가하므로 좁은 문이나 낮은 층에는 들어갈 수 없다.
- 계단의 경사 높이 자체는 블록 기준으로 고정하고, 발 위치만 현재 반경과 높이에 맞춰 해결한다.
- 일반 턱 자동 오르기 한계는 스케일에 완전히 비례시키지 않고 안전 범위 안에서만 완만하게 증가시킨다. 큰 캐릭터가 벽 한 블록을 계단 없이 자동으로 넘어가는 현상을 막기 위해서다.
- 건축 Raycast 도달 거리는 팔 길이에 맞춰 일부 증가시키되, 원거리 설치가 되지 않도록 셀 단위 최대값을 둔다.
- 플레이어와 겹치는 블록 설치 검사는 현재 스케일의 원기둥 충돌체를 사용한다.

크기 확대는 축소와 다르게 사전 검증이 필요하다. 캐릭터 그룹의 기준점이 발에 있으므로 확대 시 머리와 어깨가 위·옆으로 자란다. 확대 후 충돌체가 천장, 벽, 문틀과 겹치면 크기 변경을 적용하지 않고 “이 공간에서는 더 커질 수 없어요”라고 안내한다. 축소는 항상 허용한다.

최대 크기 `0.70`은 기본 크기의 2.5배다. 이 상태의 캐릭터 지름은 현재 2셀 문 유효 폭보다 커질 수 있으므로, 큰 캐릭터가 모든 실내 공간을 통과하도록 충돌체를 억지로 줄이면 안 된다. 대신 HUD에 현재 크기와 “이 출입구에는 더 작은 크기가 필요해요”를 표시하고, 선택적으로 기본 크기로 되돌리는 단축 버튼을 제공한다.

크기 변경 중 위치 안정성 규칙은 다음과 같다.

1. 발 위치는 유지하고 몸만 위로 확장·축소한다.
2. 확대 후보 충돌체로 머리와 수평 공간을 먼저 검사한다.
3. 검사 통과 시 스케일과 카메라, 충돌체를 같은 프레임에 갱신한다.
4. 계단 중간에서도 현재 support surface와 footY는 유지한다.
5. 확대가 거부되더라도 이동과 기존 스케일은 그대로 유지한다.

카메라는 이미 눈 높이와 추적 거리를 캐릭터 스케일에 일부 연동하므로 이 계산을 공통 `characterDimensions` 결과에 연결한다. 이렇게 해야 렌더 크기, 충돌 크기, 카메라 높이, 조준 시작점이 서로 다른 비율로 움직이지 않는다.

멀티플레이 표시도 보완해야 한다. 현재 원격 캐릭터는 항상 기본 스케일로 렌더링되고 위치 동기화에도 크기가 포함되지 않는다. 빌더 안에서 다른 방문자에게 실제 크기를 보여줄 필요가 있다면 presence 데이터에 정규화·범위 제한된 `scale`을 추가하고, 원격 캐릭터의 렌더 크기와 보행 높이에 동일하게 적용한다. 단, 이동 충돌의 최종 판정은 각 로컬 캐릭터에서 수행하므로 건축 저장 포맷은 변경하지 않는다.

### 4.3 `walkHeightAt(x,z)`를 상태 있는 이동 해결기로 바꾼다

현재의 위치만 받는 높이 함수는 위층과 낙하를 구별할 수 없다. 이동 해결기는 최소한 다음 입력을 받아야 한다.

- 현재 위치와 현재 발 높이
- 이동 희망 XZ
- 수직 속도와 grounded 상태
- 플레이어 반경과 키
- 셀 캐시와 부지 정보

결과는 다음 상태를 반환한다.

- 확정된 X, footY, Z
- `grounded`
- `verticalVelocity`
- `supportCell`, `supportKind`
- 충돌한 블록과 막힌 축

이동 순서는 고정한다.

1. 프레임 이동량을 안전한 소구간으로 분할
2. 희망 XZ에서 몸통 수평 충돌 검사
3. 현재 발 높이 주변의 유효 지지 표면 탐색
4. 일반 턱의 `maxStepUp`, 계단 경사, 하강 범위 판정
5. 새 footY에서 머리 공간 검사
6. grounded/낙하 상태 갱신
7. X/Z 축별 미끄러짐 후 최종 위치 확정

`highest occupied`는 사용하지 않는다. 현재 발 높이와 연결 가능한 `valid support surface`만 선택한다.

### 4.4 계단은 시각 형상과 보행 형상을 분리한다

기존 1셀 계단 외형과 저장 타입은 유지한다. 보행에는 부드러운 1셀 경사 프록시를 사용한다.

- 셀 중심 기준으로 플레이어 좌표를 계단 로컬 좌표로 변환한다.
- 회전을 제거한 공통 좌표계에서 낮은 쪽→높은 쪽 진행률을 구한다.
- 진행률로 경사 표면 높이를 계산한다.
- 계단 양옆과 높은 쪽 벽면은 몸 충돌 형상으로 처리한다.
- 낮은 쪽 진입, 높은 쪽 하강, 옆면 충돌, 계단 위 천장 조건을 각각 검증한다.

기존 계단은 한 셀 전진하며 한 셀 상승하는 45도 구조다. 1차에서는 기존 외형과 부지 크기를 존중해 유지한다. 사용성 테스트에서 지나치게 가파르면 저장 타입은 유지한 채 2셀짜리 계단 모듈을 별도 배치 도구로 추가한다.

### 4.5 낙하는 명시적인 정책으로 처리한다

위층 가장자리에서 아래 지면을 즉시 선택하면 순간이동이 생긴다. 반대로 현재 높이를 유지하면 공중 보행이 생긴다. 기존 점프의 수직 속도 상태를 확장하여 지지 표면이 사라지면 중력을 적용하고, 아래 표면과 만날 때 착지시킨다.

1차 안전 기준:

- 작은 바닥 단차는 자동 보정
- 한 셀짜리 수직 블록은 자동 오르기 금지
- 계단은 방향성 경사로만 상승
- 지지 표면이 없으면 낙하
- 부지 플랫폼 아래로 떨어지면 기존 지형에 착지

### 4.6 설치 좌표는 Raycast 결과가 결정한다

세 층 상태를 분리한다.

| 상태 | 역할 |
| --- | --- |
| `playerLayer` | 현재 발 위치 표시와 기본 안내 |
| `targetLayer` | Raycast가 실제로 가리키는 설치 대상 |
| `manualLayer` | 설계도 모드에서만 사용하는 고정 층 |

플레이-빌드 대상 선택 순서는 다음과 같다.

1. 카메라에서 화면 중앙으로 Raycast
2. 가장 가까운 블록 또는 플랫폼 hit 선택
3. hit의 로컬 면 법선을 월드 방향으로 변환하고 6축으로 정규화
4. 일반 블록은 `hitCell + faceNormal`을 후보로 설정
5. 계단 높은 쪽 윗면은 기존의 전방+한 층 위 규칙 적용
6. 반투명 미리보기와 유효/무효 이유 표시
7. 사용자가 확정할 때만 편집 실행

측면, 아래면, 윗면을 모두 처리하되 블록 카탈로그의 `buildFaces`를 따른다. Raycast 최대 거리는 셀 4~5개 범위로 시작해 실제 캐릭터 크기에 맞춰 조정한다.

### 4.7 배치 검증은 한 함수로 통합한다

현재는 사실상 “비어 있음 + 블록 수 제한”만 검사한다. 설치 미리보기와 실제 편집이 서로 다른 판단을 하지 않도록 공통 검증 결과를 사용한다.

필수 검사:

- 부지와 높이 범위 안인가
- 후보 셀이 비어 있는가
- 360블록 제한 이내인가
- 플레이어의 발·몸·머리와 겹치지 않는가
- 허용 설치 거리와 시야 안인가
- 대상 면이 부착 가능한가
- 문 2셀 출입구의 예약 공간을 침범하지 않는가
- 계단 도착부에 필요한 머리 공간이 있는가

서버는 현재 전체 그리드의 타입, 비트, 크기, 블록 수, 리비전을 검증하지만 구조적 배치 규칙까지 검증하지 않는다. 현 단계가 단일 소유자 편집이므로 1차는 클라이언트 검증으로 충분하다. 공동 편집·경쟁 요소를 도입할 때 동일 규칙의 서버 검증을 추가한다.

## 5. 프로젝트에 맞춘 모듈 책임

### `astraBuilderModel.js`

- 그리드 좌표, 인코딩, 편집, 순수 데이터 변환만 유지
- 블록 번호 직접 비교를 점진적으로 카탈로그 조회로 교체
- 기존 저장 포맷과 공개 함수의 호환 계층 제공

### 신규 `astraBuilderBlockCatalog.js`

- 블록별 렌더·충돌·지지·조준·배치 규칙의 단일 출처
- 서버 저장값에는 포함하지 않는 런타임 정적 정의

### 신규 `astraBuilderPhysics.js`

- 셀별 단순 충돌체 생성
- 주변 셀 조회 캐시
- 평면/계단 지지 표면 샘플링
- 캐릭터 원기둥 대 블록 충돌
- 머리 공간, 상승, 하강, 낙하, 축별 미끄러짐 해결
- React/Three 객체에 의존하지 않는 순수 함수로 작성하여 Node 테스트 가능하게 구성

### 신규 `astraBuilderTargeting.js`

- hit 정보에서 월드 면 법선과 후보 셀 계산
- 계단 연속 설치 규칙
- 배치 검증과 무효 이유 코드
- 미리보기와 실제 편집이 같은 결과를 사용

### `GalaxyWorld3D.jsx`

- `Astronaut`에 빌더 전용 3D 이동 해결기를 주입
- 빌더 활성 상태를 `paused`와 분리
- 캐릭터의 `footY`, `grounded`, `playerLayer` 상태 연결
- 모바일 조이스틱을 빌더 중에도 유지
- 기존 충돌/지형 이동은 부지 밖에서 그대로 사용하여 회귀 범위를 제한

### `AstraBuilderPlot.jsx`

- 기본 모드는 수동 편집 plane 이벤트가 아니라 화면 중앙 Raycast 미리보기 사용
- 기존 plane과 Orbit 카메라는 설계도 모드에서만 활성화
- 블록 렌더 인스턴스와 외곽선은 그대로 재사용

### `AstraBuilderHud.jsx`

- “건축/카메라”를 “플레이-빌드/설계도”로 명확히 변경
- 현재 층과 조준 층을 구분해 표시
- PC와 모바일용 설치·삭제·회전 조작 제공
- 무효 미리보기 사유를 짧은 문구로 표시

### 저장·동기화 계층

`useAstraBuilderPoc.js`, codec, 로컬 복구, 서버 lease/revision 저장은 1차에서 변경하지 않는다. 물리 규칙은 정적 카탈로그이므로 기존 `u16le-v1` 데이터가 그대로 동작한다.

## 6. 입력과 카메라 정책

### PC

- WASD/방향키: 이동
- Shift: 달리기
- Space: 점프
- 마우스 이동 또는 우클릭 드래그: 시점
- 좌클릭/전용 키: 미리보기 위치 설치
- 삭제 도구 선택 후 확정: 대상 삭제
- Q/E: 회전
- B: 플레이-빌드
- C: 설계도 모드
- V: 1인칭/3인칭 전환 허용

브라우저 포인터 잠금은 초기 필수 사항으로 두지 않는다. 기존 카메라 입력을 먼저 재사용하고, 조준 안정성이 부족할 때 1인칭 정밀 모드에만 선택적으로 적용한다.

### 모바일

- 왼쪽: 기존 이동 조이스틱 유지
- 오른쪽 화면 드래그: 시점 조절
- 화면 중앙: 조준점과 미리보기
- 우측 액션 버튼: 설치/삭제/회전
- 실내에서는 1인칭 전환 버튼 제공

### 실내 카메라

가장 빠른 1차 해법은 기존 1인칭을 빌더에서 허용하는 것이다. 이후 3인칭 카메라와 캐릭터 사이를 Raycast하여 벽에 닿을 때 카메라를 앞으로 당기는 기능을 추가한다. 건물 내부에서 부지 중심 Orbit 카메라는 사용하지 않는다.

## 7. 개발 단계와 완료 기준

### Phase 0 — 계측과 회귀 기준 고정

작업:

- 캐릭터 실제 반경·키, 문 유효 폭, 바닥 상단, 계단 방향을 화면 디버그로 확인
- 현재 평지 이동, 점프, 충돌, 저장 테스트를 기준선으로 기록
- 개발 환경에서만 발 높이, support cell, target cell, 충돌체를 표시

완료 기준:

- 실제 수치가 문서 상수와 일치
- 기존 `test:astra-builder`와 프로덕션 빌드 통과

예상: 1~2 개발일

### Phase 1 — 블록 카탈로그와 물리 캐시

작업:

- 7개 블록의 몸 충돌·지지·조준 속성 확정
- 셀이 바뀔 때만 런타임 충돌/지지 캐시 재생성
- 기존 문 출입구 예외를 명시적 문 규칙으로 감싸기

완료 기준:

- 저장 데이터 무변경
- 기존 건축물 렌더링 무변경
- 타입 번호 분기와 물리 의미가 한 카탈로그에서 조회됨

예상: 1~2 개발일

### Phase 2 — 다층 이동과 계단

작업:

- 상태 있는 이동 해결기 도입
- 원기둥 대 AABB 충돌, 수직 범위 겹침, 머리 공간 검사
- 4방향 계단 경사와 옆면 충돌
- 위층 바닥 연결, 낙하와 착지
- 부지 밖에서는 기존 지형 이동 유지

완료 기준:

- 계단 네 방향을 오르내림
- 1층 벽은 2층 플레이어를 막지 않음
- 낮은 천장 아래 계단은 진입 불가
- 바닥 없는 곳에서 공중 보행·순간이동 없음

예상: 3~5 개발일

### Phase 3 — 캐릭터 중심 플레이-빌드 모드

작업:

- 빌더 활성과 캐릭터 pause 분리
- 기존 추적/1인칭 카메라 재사용
- PC 이동 입력과 모바일 조이스틱 유지
- Orbit 카메라는 설계도 모드로 한정

완료 기준:

- 빌더 HUD를 연 상태로 건물 안팎과 계단을 이동
- PC와 모바일에서 이동 입력이 건축 입력과 충돌하지 않음

예상: 2~3 개발일

### Phase 4 — Face Raycast와 배치 검증

작업:

- 화면 중심 Raycast와 6면 스냅
- 계단 이어 짓기, 측면 설치, 반투명 미리보기
- 도달 거리·시야·플레이어 겹침·문 예약 공간 검사
- `playerLayer`, `targetLayer`, `manualLayer` 분리

완료 기준:

- 1층에서 계단을 놓고, 올라가며 다음 계단과 2층 바닥/벽을 연속 건축
- 2층에서 1층 벽, 머리 위 천장, 측면 블록을 의도대로 조준
- 무효 위치는 설치되지 않고 이유가 표시됨

예상: 3~4 개발일

### Phase 5 — 실내 카메라·QA·최적화

작업:

- 3인칭 카메라 벽 충돌/자동 줌
- 계단과 문 경계 조작감 튜닝
- 단위·통합·모바일 수동 QA
- 셀 변경 시 캐시 갱신과 프레임 비용 측정

완료 기준:

- 좁은 실내에서 카메라가 외벽 뒤로 숨지 않음
- 60/30fps와 큰 delta에서도 벽 관통 없음
- 기존 로컬/서버 저장, undo/redo, 충돌 리비전 복구 유지

예상: 2~4 개발일

전체 예상은 숙련 개발자 1인 기준 약 12~20 개발일이다. 가장 빠른 사용 가능 버전은 Phase 0~4이며, 약 10~16 개발일 범위다. 실제 일정은 Phase 0에서 캐릭터 높이와 카메라 입력 충돌을 계측한 뒤 확정한다.

## 8. 테스트 계획

### 순수 함수 단위 테스트

- 4방향 계단의 시작·중간·끝 높이
- 평면, 얇은 바닥, 계단 지지 표면 선택
- 벽/유리/기둥/조명/문별 몸·머리 충돌
- 현재 발 높이와 연결되지 않은 높은 표면 배제
- X/Z 축별 미끄러짐
- 낙하와 착지
- 6면 Raycast 후보 좌표
- 회전된 계단의 연속 설치 좌표
- 플레이어 겹침, 거리, 부지 경계, 높이 제한

### 통합 시나리오

1. 빈 부지에서 계단 설치 → 정면 상승 → 다음 계단 설치 → 2층 바닥 설치
2. 문을 통해 실내 진입 → 좁은 복도 회전 → 내부 벽 설치
3. 계단 옆면과 높은 쪽 벽면에 충돌
4. 계단 위 낮은 천장에서 상승 차단
5. 2층 가장자리 낙하 후 1층 또는 지형에 착지
6. 2층에서 1층 블록과 3층 후보를 각각 조준
7. 플레이어 몸과 겹치는 셀 설치 차단
8. 빌더 중 undo/redo, 자동 저장, 서버 리비전 충돌 복구
9. 모바일 조이스틱 이동 중 설치 버튼 조작
10. 방문자 캐릭터가 동일 건축물 표면 높이로 표시되는지 확인

### 회귀 테스트

- 빌더 부지 밖 기존 월드 이동, 점프, 강·다리·경사 충돌
- 기존 시설 충돌과 상호작용
- 빌더 비활성 사용자와 행성 방문자 화면
- 기존 `u16le-v1` 로컬 및 서버 건축물 로드

## 9. 출시 전략

기능 플래그를 기존 `VITE_ASTRA_BUILDER_POC` 아래에 세분화한다.

1. 내부 QA: 새 물리 + 디버그 표시
2. 소수 사용자: 플레이-빌드 + 계단, 설계도 모드 유지
3. 모바일 포함 확대: Raycast와 카메라 튜닝 완료 후
4. 안정화 후: 기존 y=0 높이 함수와 2D 빌더 충돌 제거

기존 방식은 한 릴리스 동안 fallback으로 남긴다. 새 이동 해결기가 유효한 부지 안에서만 동작하도록 범위를 제한하면 메타센스 월드 전체 이동 회귀 위험을 크게 줄일 수 있다.

## 10. 이번 범위에서 제외할 항목

- 새 외부 물리 엔진 도입
- 저장 포맷 `u16le-v1` 변경
- 실시간 공동 건축과 셀 단위 서버 패치
- 열고 닫는 문과 문짝 애니메이션
- 반블록, 사다리, 엘리베이터, 물리 파괴

## 11. 최종 의사결정

구현 착수안은 다음으로 확정하는 것이 적절하다.

1. 기존 저장·동기화·렌더 인스턴스는 유지한다.
2. 빌더 중 캐릭터 정지를 가장 먼저 제거한다.
3. `walkHeightAt`을 단순 확장하지 않고 부지 전용 3D 이동 해결기로 교체한다.
4. 블록 `occupied`와 보행/충돌/조준 의미를 정적 카탈로그로 분리한다.
5. 계단은 기존 1셀 외형 + 부드러운 방향성 경사 프록시로 시작한다.
6. 설치 좌표는 Raycast가 결정하고, 층 엘리베이터는 설계도 모드에만 사용한다.
7. 문은 1차에서 항상 열린 2셀 출입구로 명시하고 상태형 문은 후속으로 미룬다.
8. 외부 물리 라이브러리 없이 순수 함수와 주변 셀 조회로 구현한다.

이 방향이 현재 메타센스 코드의 자산과 저장 호환성을 가장 많이 보존하면서, 사용자가 원하는 “캐릭터가 건물 안에서 이동하며 계단을 놓고 위층을 계속 짓는 경험”에 가장 짧게 도달하는 경로다.
