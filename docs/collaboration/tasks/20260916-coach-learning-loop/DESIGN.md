# 코드 스튜디오: 사용하면서 개선되는 오류·질문 도움 시스템

작성: 2026-09-16 · 설계 기준 · 로컬 구현 범위와 실제 동작은 [OPERATIONS.md](OPERATIONS.md) 참조 · 실운영 수집 미활성화

## 1. 목표와 판단 기준

학생의 실제 오류와 질문, 도움을 본 뒤의 행동이 누적될수록 정확한 기본 힌트의 범위와 설명 품질이 좋아진다. 매 오류를 AI로 재분석하거나 AI 답변을 그대로 자동 배포하는 시스템은 아니다. 학습 대상은 모델 가중치가 아니라 검증된 진단 규칙·설명 카드·수업별 적용 조건이다.

성공 기준은 API 호출 감소 하나가 아니다. 잘못된 설명 증가 없이 학생이 적절한 다음 행동을 할 수 있어야 한다. 규칙 개발·검토·저장·운영 비용까지 포함했을 때 재사용 가치가 있는 사례만 승격한다. 드문 복합 오류는 계속 AI 또는 선생님에게 맡긴다.

## 2. 학생이 도움을 받는 경로

1. 실행 오류 → 원본은 브라우저에서만 분석한다. 기존 실행 결과를 사용하며 진단을 위해 코드를 재실행하지 않는다.
2. 검증된 규칙을 정확한 적용 조건으로 조회한다. 예외 종류뿐 아니라 가져온 모듈, 객체 생성 방식, 호출 구조, 파일/셀 문맥, 실행기 버전을 확인한다.
3. 맞는 규칙이 있으면 해당 줄·근거·작은 다음 행동을 담은 힌트를 즉시 표시한다. 쉬운 말/예시/확인 방법도 같은 카드에 미리 저장하여 추가 AI 호출 없이 펼친다.
4. 근거가 모자라면 단정하지 않는다. 가장 비슷한 규칙을 억지로 적용하지 않고 불확실함을 표시한다.
5. 여전히 어렵다는 학생의 요청이 있을 때에만 기존 전송 가능 범위에서 Luna에 질문한다. 개인정보 경계상 전송할 수 없는 사례는 기본 점검 또는 교사 도움으로 연결한다. 개인정보 차단이 AI 강제 호출로 우회되지 않는다.
6. 힌트 이후의 수정·재실행·추가 질문·오류 상태를 관찰한다. 이 관찰은 뒤에서 규칙 개선에 사용하며 현재 도움을 기다리게 하지 않는다.

AI 추가 도움은 고확신 규칙에서도 열어 둔다. 개발자가 쉬운 오류라고 판단했다는 이유로 학생의 도움 요청을 막지 않는다. 반대로 모르는 내용을 해결한 척하지 않는다.

## 3. 무엇을 배우는가

| 누적 신호 | 개선 대상 | 유의점 |
|---|---|---|
| 같은 코드 구조의 오류가 반복됨 | 새 진단 규칙 후보 | SyntaxError라는 이름만으로 합치지 않음 |
| 기본 힌트 후 ‘무슨 뜻인지 모르겠어요’가 많음 | 설명/예시 난이도 | 진단이 틀렸다고 바로 판단하지 않음 |
| 기본 힌트 후 AI 답변이 반복해서 같은 추가 설명을 제공 | 카드의 누락된 한 단계 | 이미 지불한 답변을 재사용, 별도 실시간 호출 없음 |
| 힌트 후 같은 오류가 계속됨 | 위치 안내·진단 조건·설명 점검 | 수정하지 않고 재실행한 경우 분리 |
| 오류가 달라짐 | 중간 진전 여부 검토 | 전체 해결로 세지 않음 |
| 실행 완료 + 학생이 이해했다고 응답 | 유용성의 보조 근거 | 실행 완료만으로 개념 이해를 단정하지 않음 |
| ‘설명이 맞지 않아요’·교사 수정 | 보류/회수 및 반례 추가 | 신고 한 건도 검토, 무조건 사실로 자동 확정하지 않음 |

명시적 질문도 중요하다. 현재 UI에는 자유 질문 입력이 없으므로, 먼저 ‘무슨 뜻인지 모르겠어요 / 어느 줄을 고치나요 / 예시를 보고 싶어요 / 고쳤는데 또 오류예요 / 설명이 맞지 않아요’ 같은 질문 의도 버튼을 넣는다. 뜻·위치·예시 버튼은 검증된 카드의 다른 설명을 보여주므로 API 비용이 없다. 이 선택 자체가 설명의 약점을 알려준다.

추후 자연어 질문은 별도 입력·개인정보 처리 계약이 필요하다. 코드 전용 변환기가 자유 문장의 개인정보까지 제거한다고 가정하지 않는다. 질문 원문을 몰래 저장하거나 기존 code-schema에 끼워 보내지 않는다. 안전하게 분류할 수 있는 질문 의도만 집계하며, 원문 수집이 필요하다면 별도 고지·권한·보관 정책과 명시적 제출을 먼저 만든다.

## 4. 지속 개선 루프

관찰 → 빈도/실패 신호 집계 → 우선순위 선정 → 개선 초안 → 반례 검증 → 승인 → 소규모 적용 → 재측정 → 유지/수정/회수.

### 관찰과 집계
- `ruleId`, `ruleVersion`, `runtimeVersion`, `mode`, 고정된 질문 의도, 도움 단계(local/AI), 결과 종류, 실제 API 입력/출력 토큰 수, 상대 시간 구간만 기본 집계한다.
- 원본 코드·변수 이름·문자열·질문 원문·traceback·파일 경로는 기본 이벤트에 저장하지 않는다.
- 동일 도움에서 재시도한 이벤트는 중복 방지한다. 코드가 바뀌었는지 여부만 사용하며 소스 diff는 저장하지 않는다.
- 탭 내 임시 도움 ID로 재실행을 연결하고, 가능하면 브라우저에서 한 도움의 결과를 합쳐 한 번에 전송한다. 세션 종료·무응답·중단은 unknown으로 남긴다.
- 인증된 집계 엔드포인트는 학생이 보낸 ruleId/버전을 실제 배포 목록과 대조한다. 크기·횟수·중복을 제한한다. 학생이 통계를 과장해도 규칙을 직접 배포할 수 없다.
- 한 학생의 반복이 인기 오류처럼 보이지 않도록 내부 인증 기준 기여 상한을 둔다. 이 내부 식별값을 OpenAI로 보내지 않는다. 학생별 성적/랭킹/평가 자료로 재사용하지 않는다.

### 대표 사례와 이미 받은 AI 답변
집계만으로는 새 원인을 알아낼 수 없다. 따라서 두 저장 계층을 분리한다.

- 기본: 내용 없는 통계. 현재의 서버 메모리 응답 캐시는 장기 학습 자료가 아니므로 새 저장 기능과 구분한다.
- 검토용 대표 사례: 활성화에 필요한 고지·보관 조건을 갖춘 뒤, 전송이 이미 허용된 변환 코드 구조 + 표준 오류 + 브라우저에서 원래 이름을 복원하기 전 AI 답변만 제한적으로 보관한다. 규칙군당 소수의 사례만 저장하고 중복/유사 사례는 버린다. 개인 원문은 저장하지 않는다. 변환 자료도 무조건 익명이라고 간주하지 않는다.
- 보관 초안: 사례 14일, 임시 연결 기록 7일, 집계 90일. 실제 TTL/삭제 검증 및 접근 통제가 구현된 뒤에만 이 기간을 고지한다. 현재 적용된 기간이라는 뜻이 아니다.
- 검토자가 승인한 지식에는 실제 사례를 그대로 넣지 않고 합성 예제, 적용 조건, 반례, 설명만 남긴다. 학생의 특정 문맥이 다른 학생에게 전달되지 않는다.

### 우선순위 선정
매번 분석하지 않고, 일정 기간 모인 집계에 대해 단순 계산만 수행한다. 초기에는 운영자가 필요할 때 실행하는 보고서로 시작하고 실제 규모가 생길 때 예약 집계를 추가한다.

1. 위험/명백히 잘못된 설명 신고는 빈도와 무관하게 검토한다.
2. 일반 개선은 빈도, 실제 AI 추가 요청 수, 설명을 이해하지 못한 비율, 재사용 가능성, 수정 난이도로 우선순위를 정한다.
3. 새 데이터가 거의 없는 규칙군은 재분석하지 않는다. 기존 후보와 입력 묶음의 해시가 같으면 기존 결과를 재사용한다.
4. 개선 후보 수를 제한한다. 초기 운영 제안: 한 검토 주기에서 상위 3개까지만. 수치는 비용/수업 규모 관찰 뒤 조정한다.

### AI는 필요한 초안 작성에만 사용
- 좋은 답변이 이미 있으면 그 답변에서 카드 초안을 만들고 사람이 검토한다. 새 API 호출은 필요 없다.
- 여러 답변이 상충하거나 반복 질문의 공통 원인을 정리해야 할 때에만 Luna로 묶음 초안을 요청한다. 학생 요청과 별도 예산·중복 키를 가진다.
- 개별 사건마다 분류 AI/검토 AI/채점 AI를 연달아 호출하지 않는다.
- 출력은 허용된 규칙 스키마와 카드 문구 초안이다. JavaScript/Python 실행 코드나 정규식을 AI가 작성해 자동 실행하도록 하지 않는다.
- 자료가 부족하거나 경제성이 없으면 후보 상태로 둔다. 모든 오류 유형을 규칙화할 필요는 없다.

## 5. 규칙과 카드의 안전한 승격

규칙 초안의 필드:
- ID/버전, 지원 runtime·라이브러리·모드
- 허용된 진단기 ID와 조건: 예외 분류, 생성자/객체/호출 관계, import 근거, 실패 줄과 생성 줄의 관계
- 적용 제외 조건: 다른 셀 정의, 변수 재대입, 조건부 생성, 알 수 없는 객체 등
- 학생용 설명: 관찰 근거 → 한 가지 행동 → 짧은 예시 → 확인 질문 → 재실행 방법
- 이름/줄 번호는 브라우저에서 대입하는 슬롯. 학생 입력을 HTML로 렌더링하지 않는다.
- 합성 양성 사례와 반례, 작성 근거, 검토 상태, 배포/회수 이력

승격 단계:
`candidate → tested → teacher-reviewed → shadow → limited → active` 또는 `rejected / rolled-back`.

- AI 문구가 자연스럽다는 이유만으로 승격하지 않는다. 기존 전체 회귀 검사와 규칙별 양성/반례를 통과해야 한다.
- 예: `t = Turtle` 뒤 메서드 오류는 후보지만, 클래스 자체를 콜백이나 자료로 보관하는 정상 코드는 오류로 단정하면 안 된다. 생성자 `()` 누락과 메서드 인자 누락을 서로 구분한다.
- 초기에는 정상 수업 예제와 실패 예제를 이용한 오프라인 검증을 우선한다. shadow는 학생에게 새 설명을 보여주지 않고 기존 결과와 일치 여부만 집계한다.
- 한정 적용도 검토를 통과한 규칙만 대상으로 한다. 작은 표본의 성공률을 과신하지 않고 횟수·분모·반례를 함께 본다.
- 오진 신호가 늘면 해당 버전만 즉시 비활성화하고 이전 카드/기본 안내로 돌아간다.
- 새 조건을 기존 진단기에서 표현할 수 없으면 별도 코드 변경·검증이 필요하다. 이 부분까지 무인 자동화하지 않는다.

배포되는 것은 작은 규칙/설명 묶음이다. 학생 브라우저에서 조회하며 CDN/버전 캐시를 사용한다. 지원하지 않는 버전·알 수 없는 조건은 무시한다. 원격 임의 코드 실행이나 이벤트마다 데이터베이스 조회를 추가하지 않는다. 승인된 배포자만 버전 매니페스트를 바꿀 수 있게 한다.

## 6. 비용 판단: AI보다 비싼 규칙은 만들지 않는다

분모는 전체 오류 건수가 아니라 ‘새 규칙이 없었다면 실제 유료 AI 요청으로 이어질 것으로 예상되는 건수’다. 이미 기본 힌트로 끝나는 오류를 AI 절감 건수로 세지 않는다.

예상 순편익 = 예상 회피 유료 요청 수 × 요청당 관측 비용
              − 추가 AI 초안/검증 비용
              − 저장·집계·전송 비용
              − 개발·교사 검토·유지보수 비용.

요청당 비용은 운영 당시 실제 토큰 사용량과 요금표로 계산한다. 현재 알려지지 않은 절감률/단가로 효과를 확정하지 않는다. 개선 때문에 오진이나 추가 질문이 늘어나는 비용도 함께 본다.

- 드물고 복잡한 오류: AI를 계속 사용하는 편이 경제적일 수 있다.
- 반복되는 간단한 오류: 같은 설명을 반복 구매하지 않도록 규칙/카드로 만든다.
- 빈도가 높지만 코드 문맥이 제각각: 공통 체크 한 단계만 로컬화하고 나머지는 AI에 맡긴다.
- 교육적으로 중요한 개선: API 절감과 별도 목표로 승인하되, 비용을 숨기지 않는다.
- 예산 상한은 학생 도움 예산과 개선 작업 예산을 분리한다. 개선 예산이 소진돼도 이미 제공 중인 기본 힌트와 학생 도움의 가용 예산을 빼앗지 않는다.
- 개선 주기는 주/월 단위 후보 집계로 충분하다. 일단 요청 시 보고서로 검증하고 사용량에 따라 자동화를 도입한다. 처리할 후보가 없으면 AI 호출은 0회다.
- 자동 미세조정, 벡터DB, 상시 임베딩, 다중 모델 심사, 전체 코드 재실행은 초기 설계에서 제외한다.

## 7. 효과 측정과 잘못된 자기강화 방지

지표를 함께 본다:
- 도움 후 수정·재실행 비율
- 같은 오류 지속 / 다른 오류로 전환 / 실행 완료 / 중단·관찰 불가
- 학생의 ‘도움 됨 / 이해 안 됨 / 맞지 않음’ 선택
- 기본 힌트 이후 실제 AI 추가 요청률, AI 이후 재질문률
- 교사 검토 오진 건수, 규칙 적용 제외/보류 비율
- 실제 API 비용과 규칙 유지보수 시간을 합친 비용

‘API 호출이 줄었다’만으로 성공 처리하지 않는다. 학생이 포기해서 호출이 줄었을 수 있다. 오류 없는 실행도 코드를 지워버린 결과일 수 있고 학습 성취를 입증하지 않는다. 질문 버튼을 누르지 않은 것을 이해했다고 해석하지 않는다.

학생 피드백·AI 답변은 신뢰할 수 없는 관찰 자료다. 반복 전송, 악의적 문구, 잘못된 설명이 규칙으로 자동 승격되지 않도록 기술 검증과 교육 검토를 모두 거친다. 통계에 대한 조회 권한과 사례에 대한 조회 권한을 분리한다.

## 8. 기존 코드에 연결하는 구현 순서

### 1단계: 관찰 기반 (추가 분석 AI 호출 없음)
- ErrorCoach.jsx: 고정 질문 의도 버튼, 규칙/설명 버전, 기본 답변 카드 단계, 도움 결과 이벤트.
- 파일/노트북 실행 상태 연결: 실행 ID와 탭 내 도움 ID를 연결. 단순 출력 완료와 계속 실행되는 pygame/Tk 프로그램을 구분. 정지·셀 전환·페이지 이탈은 unknown.
- 별도 인증 집계 endpoint: 고정 스키마, 할당량/중복 검증, 원문 금지, 보관·삭제 검사. 기존 paid callable에 자동 호출 부가하지 않음.
- 교사용 최소 보고서: 자주 막히는 유형/이해 못한 설명/실제 AI 비용. 학생 개인 코드 목록이 아님.

### 2단계: 지식 개선 작업대
- 제한된 대표 사례 저장은 준비 요건을 확인한 뒤 별도 활성화.
- 검토 대상 상위 유형과 이미 받은 AI 설명을 나란히 비교.
- 사람이 문구를 바로 고칠 수 있으며, 복잡한 묶음만 Luna 초안 요청.
- 후보 카드 → 합성 예제/반례 → 기존 Node/WASM 회귀 → 승인·버전 관리.

### 3단계: 제한 배포와 운영
- 버전별 작은 배포 묶음, shadow/limited 적용, 회수 스위치.
- 일정량의 새 사례/충분한 관측이 쌓일 때만 재검토. 주기는 사용량에 맞춰 조정.
- 지속적으로 경제성이 낮은 후보는 폐기한다. 쌓이는 모든 자료를 영구 보관하지 않는다.

후속 구현에서 관찰·질문 카드·관리자 검토·버전 적용·회수·일일 삭제를 추가했다. 자동 AI 초안 생성은 추가하지 않았다. 실제 차이와 한계는 OPERATIONS.md에 기록한다. 실운영 배포와 수집 활성화는 아직 하지 않았고, ZDR/학생용 AI 활성화 상태도 변경하지 않았다.
