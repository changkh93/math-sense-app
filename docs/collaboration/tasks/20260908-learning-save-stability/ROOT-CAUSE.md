# 학습 기록 저장·완료 체크: 원인 조사와 수정

조사일: 2026-09-08. 기준 코드: `90c92a046f7f94b09e3c764da1e11341be1e4c52`.
두 학생의 기록을 복구하는 것과 별개로, 실제로 기록을 누락하거나 지울 수 있는 처리 경로를 재현하고 수정했다. 원본 답안·인증정보는 이 문서와 테스트에 포함하지 않는다.

## 1. 완료 집계 함수가 운영에서 실패하고 있었다 — 확인된 장애

`syncLearningSummary`는 변경된 단원의 history를 `where('unitId', '==', unitId)`로 조회한다. 그런데 `firestore.indexes.json`의 history.unitId 필드 예외 설정에는 COLLECTION_GROUP 인덱스만 있었고, 학생 한 명의 history 컬렉션을 조회하는 COLLECTION 인덱스는 빠져 있었다. 필드 예외를 명시하면서 기본 단일 컬렉션 인덱스도 비활성화된 상태였다.

운영 API에서 실제 설정도 동일함을 확인했다. 운영 함수 로그에는 다음 오류가 반복됐다.

```text
2026-09-08T08:45:51.794935Z syncLearningSummary
9 FAILED_PRECONDITION: The query requires a COLLECTION_ASC index for collection history and field unitId.
2026-09-08T08:47:10.013415Z syncLearningSummary
9 FAILED_PRECONDITION: The query requires a COLLECTION_ASC index for collection history and field unitId.
```

MINSOL의 해당 단원은 원본 progress/history에 본문·워크북 완료가 있지만 summary의 text만 false였다. 따라서 화면 체크만 잘못 그린 문제가 아니라, 원본 → 요약 집계 → 화면으로 이어지는 과정이 실제로 끊겨 있었다. 문서 개수나 최근 수정 시각만으로 정상 여부를 판단하면 이런 일부 항목 누락을 놓칠 수 있다.

수정:

- history의 unitId/chapterId/regionId에 COLLECTION ASC/DESC를 추가하고 기존 COLLECTION_GROUP 인덱스를 보존했다. 운영에도 이 6개 인덱스만 추가했다. 학생 데이터나 기존 인덱스를 삭제하지 않았다.
- 새 집계 구현은 오래된 구현 버전의 summary를 원본 history/progress로 다시 만든다. 명시적인 무결성 점검 요청은 단순 개수·시각 비교 대신 원본과 재조정한다.
- 현재 보이는 지역의 완료 상태는 해당 단원의 원본 progress 문서도 제한된 묶음으로 구독한다. 요약 집계 지연이 완료 체크 누락으로 바로 이어지지 않도록 한다. 페이지 보상이나 미완성 답안을 전체 완료로 간주하지 않는다.

## 2. 불러오기와 저장의 순서가 보장되지 않았다 — 기존 코드로 유실 재현

기존 WorkbookPlayer는 서버 기록을 읽는 동안에도 초기 빈 화면과 종료 버튼을 사용할 수 있었다.

1. 화면이 빈 답안과 1페이지 상태로 열린다.
2. 서버에서 기존 9페이지 기록을 읽는 작업이 아직 끝나지 않는다.
3. ‘오늘은 여기까지’를 누르면 초기 빈 답안을 저장하고 화면을 닫는다.
4. 뒤늦게 도착한 기존 기록은 unmount 취소 처리로 폐기된다.

또 다른 경로도 있었다. 서버 읽기에 실패하고 로컬 캐시가 없으면, 불러오기가 성공한 것처럼 `progressHydrated=true`가 되어 빈 상태의 자동 저장이 시작됐다.

`merge:true`는 이 문제를 막지 않는다. Firebase SDK가 만드는 실제 write mask에서 `workbookSession.answers`와 `checkedPages`에 빈 맵을 쓰면 기존 맵 전체를 지운다. 테스트에서 **답안은 사라지고 별도 보상 합계는 남는 현상**을 재현했다. 이는 GOOD LUCK의 운영 문서에서 확인된 ‘9페이지 기록 → 더 새로운 빈 기록, 보상 원장은 유지’ 형태와 일치한다.

다만 학생의 당시 브라우저 로그가 없어 두 경로 중 정확히 어느 경로를 밟았는지는 확정하지 않았다. ‘오늘은 여기까지’를 눌렀다는 제보와 충돌하는 X 버튼 단독 원인으로 설명하지 않는다.

수정:

- 서버 기록 확인 전에는 편집·채점·저장 종료를 시작할 수 없다. 읽기 실패는 빈 신규 기록으로 처리하지 않고 재시도 화면에 남긴다.
- 단순히 워크북을 열었다는 이유로 빈 기록을 자동 저장하지 않는다.
- 최신 시각만 비교하지 않고 실제 학습 내용이 있는 기록을 우선한다. 교재 구성이 달라진 경우 답안을 임의 이식하지 않는다.
- 저장을 직렬화하고 서버 응답을 받은 뒤 닫는다. 저장 중 추가된 수정도 차례로 반영한다.
- 로컬 저장소 용량 오류와 서버 저장을 분리했다. 로컬 캐시 저장 실패가 서버 저장 자체를 막지 않는다.
- 서버 revision을 트랜잭션에서 비교해 다른 창·기기의 변경을 덮어쓰지 않는다. 충돌한 로컬 답안은 별도 보관한다.
- 서버 규칙에도 기존 의미 있는 세션을 빈 세션으로 바꾸는 업데이트 차단을 추가했다. 이 규칙은 배포 후 오래 열린 구버전 화면의 빈 덮어쓰기도 차단한다. 정상 완료 후 임시 세션 정리는 허용한다.

## 3. 페이지 보상과 답안이 따로 저장됐다 — 중간 중단 구간 제거

기존에는 페이지 채점 보상을 먼저 트랜잭션으로 저장하고, 답안·채점 상태는 React 상태 갱신 뒤 별도 자동 저장으로 보냈다. 둘 사이에서 종료·통신 실패가 생기면 보상은 있지만 답안이 없는 상태가 가능했다.

수정 후에는 기존 보상 트랜잭션에 해당 페이지의 답안·채점·시도 횟수·누적 보상 카운터를 함께 넣는다. 전부 저장되거나 전부 실패한다. 보상 산식과 기존 중복 지급 방지 키는 유지한다. 화면은 서버가 반환한 확정 카운터를 사용한다.

검증에서 트랜잭션을 중간에 실패시켰을 때 답안과 보상이 모두 미반영되고, 재시도·중복 호출 후에는 한 번만 반영되는 것을 확인했다.

## 4. 집계 이벤트의 중복·역순·전체 재계산 경합에 취약했다

기존 집계는 전달된 before/after 차이를 그대로 더하고 빼는 방식이었다. 같은 이벤트가 재전송되면 통계가 중복 반영될 수 있었고, 전체 재계산의 읽기와 쓰기가 분리돼 증분 집계 결과를 오래된 전체 스냅샷으로 덮어쓸 수 있었다. 재시도만 켜는 것으로 해결되지 않는다.

수정:

- 전체 재계산의 history/progress 읽기와 summary 쓰기를 하나의 Firestore 트랜잭션으로 묶었다.
- 원본 스냅샷의 정확한 읽기 시각과 세대를 기록한다.
- history 문서별 적용 이벤트 ID·버전을 summary와 같은 트랜잭션에 기록한다. 원본 답안을 별도 복제하지 않는다.
- 이미 전체 재계산에 포함된 이벤트와 중복 이벤트는 건너뛴다. 실제 원본이나 이전 버전이 맞지 않으면 현재 원본으로 재계산한다.
- 실패한 트랜잭션은 적용 기록도 남기지 않는다. 이 조건을 검증한 뒤 함수 재시도를 활성화했다.
- 완료 플래그는 원본 증거와 기존 정상 완료를 보존한다. 점수·보상·학습 이벤트를 새로 만들어 복구하지 않는다.

비용 변화: 일반 이벤트에 작은 적용 기록 문서 읽기/쓰기와 해당 단원 progress 읽기가 추가된다. 전체 재조정은 학생의 history/progress를 읽으므로 단순 count 점검보다 비용이 든다. 기존 클라이언트의 정기 요청 간격을 유지하고, 정상 증분 이벤트는 해당 단원에 한정하며, 잦은 영상 progress 변경마다 전체 재계산하는 트리거는 추가하지 않았다.

## 운영 적용 범위와 남은 릴리스

- 두 학생의 근거 있는 기록 복구는 이전 단계에서 완료했다. 자세한 복구·재조회 결과는 STATE.md에 있다.
- 이번 단계에서 운영 history 단일 컬렉션 인덱스 6개를 추가했다. 실제 준비 상태와 조회 확인 결과는 STATE.md의 최신 항목을 따른다.
- 프런트엔드·새 집계 함수·Firestore 규칙의 코드는 수정하고 검증했지만 아직 배포하지 않았다. 현재 체크아웃에는 별도 작업의 미배포 기능도 포함돼 있어 이번 조사 결과를 전체 운영 배포 완료로 표현하지 않는다.
- 다음 릴리스에는 `syncLearningSummary`, `getOrRebuildLearningSummary`, Firestore 규칙, 웹 번들이 필요하다. 함수는 두 개만 지정해 배포할 수 있다. 규칙과 웹 전체 배포는 저장소의 다른 미배포 변경과 함께 릴리스 범위를 검토해야 한다.
- 운영 배포 후 실제 완료 집계 성공 로그, 학생의 재개 위치, 재접속 후 답안 보존을 확인해야 한다. 원본 학생 기기에서 발생했던 정확한 타이밍과 양쪽 저장소를 모두 사용할 수 없는 상태에서의 브라우저 강제 종료까지 검증된 것은 아니다.

과거 문서 조회에서 화면과 일치하는 상태를 확인했다. 2026-09-08 17:30 및 17:35 KST 스냅샷(마지막 수정 17:26:31.957)에 답안 16개, currentIdx=1, originalTotal=20, 광석 31, retryCount=3이 저장돼 있었다. 답안 16개는 모두 이해 상태 선택까지 끝난 기록이었다. 당시 미응답 문항은 10·14·17·19번이었다. 즉 안내에만 16이라고 쓰인 빈 복구가 아니라 실제 답안 16개가 존재했다.

수정한 동작:

- 현재 묶음의 문항 ID 순서를 인덱스와 함께 저장한다. 일반 저장, 중단 저장, 미완료 묶음 전환 모두 포함한다.
- 복원 시 답안과 이해 상태를 대조해 완료한 문항은 재개 대상에서 제외한다. 채점은 끝났지만 이해 상태 선택 전인 문항은 기존 잠금 화면으로 복원한다.
- 예전처럼 문항 ID 묶음이 없는 세션도 기존 답안을 유지하며 미완료 문항으로 재개한다. 위 스냅샷에서는 16개 답안·31광석을 유지하고 4문항으로 재개한다.
- 안내를 ‘답안 16/20개 복구, 미완료 4문항 재개’로 구체화하고, 상단 ‘현재 문항 1/4’와 ‘전체 답안 16/20’을 구분한다.
