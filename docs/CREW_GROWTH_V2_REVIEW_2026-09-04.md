# Study Crew 초대 이벤트 구현 리뷰 · 2026-09-04

## 범위와 결과

사용자가 구현한 미커밋 변경을 기준으로 검토하고, 이벤트 정산·재가입 방지·추천 신청 흐름의 결함을 수정했다. 운영 배포, 운영 DB 조회·마이그레이션·보상 지급은 실행하지 않았다. 기존 변경을 되돌리지 않았다.

학생 신청 흐름은 **초대 입장 → 간편 신청 → 운영자 전화 확인 → 체험 안내**다. 부모님 회원가입으로 이동시키지 않는다. 이름·학년·보호자 연락처만 받으며, 사전 보호자 동의 체크박스나 함께 작성하라는 조건은 없다. 신청은 확인 완료가 아니므로 서버에는 `phoneVerificationStatus: pending`을 저장하며 동의 완료 기록을 만들지 않는다. 운영자의 실제 전화 확인은 기존 상담 업무에서 처리한다.

## 추천 신청과 운영 정보

- 신규 `getCrewGuestTrialOffer`는 혜택 여부와 기간, 기존 접수 여부만 반환한다. 추천인 이름·전화번호·UID는 반환하지 않는다.
- 신규 `submitCrewGuestTrial`은 익명 게스트 계정과 저장된 초대를 확인한다. 유효한 추천은 28일, 추천이 확인되지 않는 일반 초대는 기존 7일 혜택으로 구분한다.
- `applications/crew_guest_{uid}`의 결정적 ID로 중복 클릭·재시도를 한 건으로 처리한다. 신청과 `referrals` 기록은 같은 트랜잭션에 저장한다.
- 운영 신청 목록에서 추천 학생 UID·학부모 UID·초대 ID와 전화 확인 필요 표시를 확인할 수 있다.
- 만료되거나 중지된 게스트 세션은 새 신청을 할 수 없다. 신청 접수만으로 수강 권한을 자동 개통하지 않는다.
- 추천 혜택과 이벤트 인원 인정은 분리한다. 체험 신청 여부를 방문 인정의 추가 장벽으로 만들지 않는다.

## 유지한 이벤트 정책

- 캠페인 최초 소속 크루 잠금은 보존하며, 탈퇴·강퇴 후 동일/다른 크루 가입으로 상실된 자격이 복원되지 않는다.
- 정회원은 잠금 이후 최소 48시간, 목표 달성 이후 고정 명단 검증은 추가 48시간이다.
- 20명 단계 +1,000, 40명 단계 +4,000. 이전 단계 미수령분 따라잡기 및 과거 지급 소급 처리는 없다.
- 게스트는 각 3분 이상인 서로 다른 세션 2회 이상, 세션 간 30분 이상, 누적 foreground 10분 이상을 요구한다. 배틀 횟수를 요구하지 않는다.
- 해당 단계의 claim이 있으면 재지급하지 않는다. 지급 대상자를 임의로 잘라 일부만 지급하지 않는다.

## 비용 개선과 한계

일반 진행률 조회는 크루 집계와 요청자 자격 확인 위주이며 전체 명단을 재조회하지 않는다. 재계산은 가입·탈퇴·게스트 자격 전환·관리자 검토·예약 시점에 수행한다. heartbeat 주기는 60초이며 겹치는 클라이언트 요청을 피한다. 바뀌지 않은 집계는 다시 쓰지 않는다. 이는 구조적 요청량 절감이며 실제 운영 청구액 감소율을 측정한 것은 아니다.

`systemConfig/crewGrowthEvent.rewardEnabled: false`로 지급을 중지할 수 있다. 선택적 `maxTierPayoutOre`를 초과하거나 큰 지급 작업은 보류한다. **캠페인 전체 누적 예산을 원자적으로 차감하는 기능은 아직 없다.** 예산값은 임의로 설정하지 않았다.

## 출시 전 남은 중요 점검

1. **대량 게스트 생성 방어:** 기존 설치 ID/IP 검사에는 제한된 쿼리와 동시 입장 경쟁 가능성이 남는다. 계정·브라우저 데이터 재생성을 사람 단위로 완전히 차단하지 못한다. 반복 입장 자동화와 정상 학교 공용망을 구분하는 운영 검토가 필요하다. App Check는 요청 출처 방어를 보완하지만 사람의 유일성을 보장하지 않는다. 적용 전 클라이언트 토큰 준비와 관측을 확인한다. [공식 Functions App Check 문서](https://firebase.google.com/docs/app-check/cloud-functions)
2. **정산 처리량:** 예약 작업의 50개 조회 제한은 대량 보류 크루가 생기면 후속 크루를 지연시킬 수 있다. 확대 전 페이지 처리 또는 보류 재시도 시각 분리가 필요하다.
3. **실제 무료체험 개통:** 기존 운영 절차가 새 학생 신청 건에 대해 전화 확인 후 28일을 적용하는지 스테이징에서 확인한다. 현재 모달은 신청 접수이지 즉시 개통 기능이 아니다.
4. **혜택 변경 경쟁:** 화면에서 4주 혜택을 조회한 직후 초대가 비활성화되면 서버의 최종 신청 판정은 달라질 수 있다. 초대 회수 운영에서는 기존 접수 혜택을 확인해야 한다.
5. **진행률의 즉시성:** 시간 경과 및 만료는 예약 재계산 시 반영될 수 있다. 지급 직전 자격은 다시 검증하지만 화면의 집계가 항상 실시간이라고 안내하면 안 된다.
6. **전환 측정:** 운영 우선 지표는 방문자 수뿐 아니라 `추천 신청 → 전화 연결 → 체험 시작 → 체험 지속`이다. 현재 기록으로 신청 귀속은 가능하지만 이 전체 퍼널 대시보드는 구현하지 않았다.

## 검증 및 배포 순서

- `npm run test:crew-growth`: 정책·정산·신청 회귀 테스트 21개 통과. Firestore 메모리 대역의 읽기/쓰기 순서 검사와 반복 실행 검증이며 실제 Emulator 동시성 검증을 대체하지 않는다.
- 수정 프런트엔드 파일 대상 ESLint 및 `node --check functions/index.js` 통과.
- 최종 `npm run build` 통과. 기존 대형 청크 및 오디오 라이선스 문서 경고는 남아 있으며 이번 신청 흐름의 빌드 오류는 없다.
- 로컬 격리 화면에서 실제 모달을 가짜 callable 응답으로 렌더링하여 신청/완료 흐름 확인. 운영 신청 데이터는 만들지 않았다.
- 최종 모바일 390px 프레임에서 체크박스 없이 세 필드만 입력하여 완료 화면과 포커스 이동 확인.
- 재현용 `node scripts/preview-crew-trial.mjs`의 `/crew-trial-qa`, `/crew-trial-qa-mobile`은 Firebase 통신 없이 UI만 검증한다.

배포 담당자는 스테이징에서 Rules·익명 인증·callable·관리자 목록·정산을 연결 검증한 뒤 진행한다. 기존 참여 잠금 초기화는 `scripts/backfill-crew-growth-v2-locks.mjs --dry-run` 결과부터 확인하고, 충돌 해결 후 승인된 시점에만 `--apply`한다. 새로운 서버 함수가 준비되기 전에 새 신청 UI만 먼저 배포하지 않는다. 대규모 프로모션은 위 남은 방어·예산·처리량 확인 후 확대한다.
